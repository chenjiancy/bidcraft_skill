# M1 素材库 · 操作手册

> 适用：bidcraft skill（标书匠）· 模块 M1 素材库
> 形态：纯文件系统 + 对话式 agent 驱动
> 对应需求：`references/M1-素材库-需求对齐.md`（v1.0 定稿）

---

## 一、这套东西怎么分工

| 角色 | 负责什么 | 载体 |
|------|----------|------|
| **脚本（确定性）** | 建目录、台账读写、收件箱登记、改名、移动、回收站、巡检、检索 | `scripts/bidcraft.py` + `bidcraft_core.py` + `bidcraft_naming.py` |
| **agent（语义）** | 看懂证书内容、判断归类、抽关键字/日期、识别企业名、判断是否同一份证书的多页、按规则写提案 | WorkBuddy / 豆包等 |
| **用户（决策）** | 确认命名与路径、选定多页分组、决定重传还是归档、同名冲突取舍 | 对话 |

依赖：**Python 3.8+ 标准库**，无第三方包，无需虚拟环境。

命令统一形态：

```bash
python scripts/bidcraft.py [--root <软件根>] [--enterprise <企业目录名>] [--json] <子命令> [参数]
```

- `--root` 缺省取环境变量 `BIDCRAFT_LIB_ROOT`，再缺省取 `<当前目录>/素材库`。**`--root` 指软件根**（如 `E:\监理标书制作`）；素材库位于 `<软件根>/<企业>/企业级/业绩库`（三层结构），仓库内不保留占位目录。
- `--enterprise` 缺省时：**只有一个企业则自动选中**；多个企业必须显式指定。
- `--json` 输出机读结果，agent 解析用；不加则输出中文表格，用户看。

## 二、标准流程（agent 编排脚本）

> 对应需求中的五阶段：① 进入企业 → ② 合规巡检 → ③ 用户确认 → ④ 收件箱上传 → ⑤ 归档

### 阶段 0｜首次调用：创建企业

```bash
python bidcraft.py init-enterprise --name "马鞍山XX工程监理有限公司"
# 重名时： --credit-code 123456   → 目录名 马鞍山XX工程监理有限公司_123456
```

自动生成：`资质/ 人员/ 业绩/ 荣誉/ 财务/ 收件箱/ 回收站/` + `素材台账.csv` + `素材台账.json` + `_素材库信息.json`。**幂等**，重复执行只做补齐。

```bash
python bidcraft.py list-enterprises     # 看有哪些企业
python bidcraft.py overview             # 台账条数 / 分类分布 / 收件箱 / 回收站概览
```

> **对话要点**：调用 skill 时若无企业，先问用户「用哪个企业名建库？」，再执行。

### 阶段 ①｜进入企业

选定企业后，把 `--enterprise <企业目录名>` 带到后续所有命令（单企业可省略）。本会话即「锁定」在该企业，素材天然隔离。

### 阶段 ②｜合规巡检

```bash
python bidcraft.py inspect --json
```

返回三类问题：

| 类型 | 含义 | 处理 |
|------|------|------|
| **非常规上传** | 文件在分类目录里，但**台账无记录**（没走收件箱、直接丢进来的） | 用户决定：删除重传 / 保留归档 |
| **命名不规范** | 台账里有，但文件名不符规范 | 按建议格式改名并更新台账 |
| **企业归属疑似不符** | 文件名疑似写着别家企业 | 弹窗提醒，用户确认 |
| **台账悬空** | 台账有记录、磁盘上文件没了（被手工删/移） | 从台账清理或找回 |

> **对话要点**：把清单原样呈现给用户，逐条问「删除重传」还是「保留归档」。

### 阶段 ③｜用户确认

按用户选择分别落到：`trash`（入回收站）或重新走「阶段 ④⑤」归档。此阶段只做决定，不动文件，除非用户明确说删。

### 阶段 ④｜收件箱上传（每次一张，不批量）

两种上传方式**都支持**（需求：上传方式不限）：

**方式 A：逐张登记（顺序权威，推荐）**

```bash
python bidcraft.py open-inbox --note "张三证书一批"
python bidcraft.py upload --file "D:/下载/张三身份证正面.jpg"
python bidcraft.py upload --file "D:/下载/张三身份证背面.jpg"
...
python bidcraft.py close-inbox
```

- 每次 `upload` 只接收**一个文件**；传目录会报错，从机制上杜绝批量。
- 每张登记 `序号 / 写入时间 / 大小 / sha256`，**序号即权威顺序**，P0/P1 不会错。

**方式 B：直接把文件拷进收件箱文件夹**

```bash
python bidcraft.py open-inbox
# 用户手动把文件复制到 <企业>/收件箱/
python bidcraft.py sync-inbox     # 补登记，按写入时间排序
python bidcraft.py close-inbox
```

- 同秒写入会提示「顺序无法自动判定」，归档前请人工确认先后。
- 内容重复（sha256 相同）会一并列出提醒。

> **对话要点**：`close-inbox` 等于「用户关闭收件箱」，此后文件处于**暂存**状态，可随时 `open-inbox` 继续补传（新批次会自动接管仍在收件箱里的文件，不会丢跟踪）。

### 阶段 ⑤｜归档（半自动确认制）

```bash
# 1) 生成建议
python bidcraft.py propose --out 归档提案.json

# 2) agent 按需修正提案（见下「提案字段」），再把结果给用户确认
# 3) 用户确认后执行
python bidcraft.py apply --proposal 归档提案.json
```

`propose` 输出（同时写入 `<企业>/收件箱/_归档提案.json`）：

```json
{
  "enterprise": "马鞍山和县监理测试有限公司",
  "owner": "马鞍山和县监理测试有限公司",
  "batch_id": "4f5f50ff",
  "time_collision": false,
  "group_hint": {"张三身份证": [2, 3]},
  "items": [
    {
      "seq": 1,
      "inbox_file": "营业执照扫描件.jpg",
      "original_name": "营业执照扫描件.jpg",
      "sha256": "…",
      "decision": "archive",
      "category": "资质", "subtype": "营业执照",
      "person": "", "project_folder": "",
      "keywords": [], "dates": ["20281231"],
      "date_type": "到期日", "page": null, "group_id": "",
      "final_name": "", "on_conflict": "keep_both",
      "ownership": "unknown",
      "needs_input": ["字段不足：…"],
      "note": ""
    }
  ]
}
```

**提案字段（agent / 用户可改）**

| 字段 | 说明 |
|------|------|
| `decision` | `archive` 归档 / `skip` 本次跳过（留在收件箱） / `delete` 删除（入回收站） |
| `category` | 大类：资质 / 人员 / 业绩 / 荣誉 / 财务（动态扩展也可填新类名） |
| `subtype` | 子类，见 `python bidcraft.py rules` |
| `person` | **人员必填**，作为 `人员/<姓名>/` 目录 |
| `project_folder` | **业绩必填**，`项目全名关键字_签订日期_总监` |
| `keywords` | 关键字列表（系统已给建议，可改） |
| `dates` | 日期列表（8 位 / `长期` / `日期不详`） |
| `page` | 多页序号；单页填 `null` |
| `group_id` | 多页分组标识；同一组填相同值（人工圈选） |
| `final_name` | 填了就完全用这个名字，不再套模板 |
| `on_conflict` | **同名判定（同大类+同子类+关键字相同）时初始为空，必须由用户确认**：`keep_both`（加序号并存）/ `trash_old`（旧文件入回收站）/ `skip`；非同名默认 `keep_both` |
| `is_name_conflict` | `true`＝脚本判定为关键字同名素材；未确认 `on_conflict` 时 `apply` 会拒绝（对话检查点） |
| `conflict_with` | 与哪些已有素材同名（`rel_path` 列表） |
| `conflict_in_batch` | `true`＝本批次内也存在同关键字条目 |
| `needs_input` | 脚本提示的「还缺什么」，补齐后清空 |

`apply` 执行内容：**改名 → 移动 → 写台账 → 清空已处理的收件箱条目**；被 `delete` 或 `on_conflict=trash_old` 顶掉的文件进 `回收站/`。

## 三、多页归组（P0/P1）

规范：多页文件末尾加 `_P0/_P1`，**P0 为首页**，按上传顺序排列。

做法（需求定：手动圈选）：

1. `propose` 会给出 `group_hint`（按主体名相似的弱启发，仅提示，不作准）。
2. agent 把同组文件列给用户，用户确认「这几张是同一份证书」。
3. agent 给该组条目设同一个 `group_id`，并按顺序设 `page=0/1/2...`。
4. `apply` 落盘为 `张三/注册证书/监理工程师_20270101_20280101_P0.jpg`、`…_P1.jpg`。

> 顺序优先级：`upload` 登记的序号 > 写入时间 > 人工指定。同秒或同源不明时，必须让用户确认。

## 四、命令速查

| 命令 | 作用 |
|------|------|
| `init-enterprise --name X [--credit-code Y]` | 建/补齐企业（幂等） |
| `list-enterprises` | 列出企业 |
| `overview` | 概览（台账/分类/收件箱/回收站） |
| `open-inbox [--note M] [--force]` | 打开收件箱（新批次，自动接管遗留文件） |
| `upload --file P [--name N]` | 逐张上传（单文件） |
| `sync-inbox` | 补登记直接拷进收件箱的文件 |
| `close-inbox` | 关闭收件箱 |
| `inbox-status` | 查看当前批次 |
| `propose [--out F] [--allow-open]` | 生成归档建议 |
| `apply --proposal F [--allow-open]` | 执行归档 |
| `inspect` | 巡检（非常规上传/命名/归属/悬空） |
| `query [--category C] [--subtype S] [--keyword K] [--owner O] [--expires-before D] [--expires-after D]` | 检索台账 |
| `trash --path 资质/xxx.jpg [--reason R]` | 移入回收站 |
| `cleanup-trash [--days 30]` | 清理超期回收站 |
| `rules [--category C]` | 打印命名规范表 |
| `validate --category C [--subtype S] --name F` | 校验单个文件名 |
| `classify --name F` | 按文件名智能判断归类与字段 |
| `build-name --category C [--subtype S] --keyword K… --date D… [--page N] [--ext E]` | 拼出规范文件名 |
| `build-project-folder --project P --date D [--director X]` | 拼业绩项目文件夹名 |
| `ownership-check --name F [--text T]` | 企业归属校验（`--text` 传正文/OCR 文本） |

退出码：`0` 成功；`1` 参数/状态错误（企业不存在、收件箱未关等）；`2` 部分条目归档失败（详见输出）。

## 五、命名规范速查

> 有效期一律填**到期日**（8 位 `YYYYMMDD`）；无到期日填 `长期`；日期不可考填 `日期不详`。
> 多页末尾加 `_P0/_P1`。关键字中的 `_` 与 `/ \ : * ? " < > |` 一律替换为 `-`。

| 大类 | 子类 | 命名 |
|------|------|------|
| 资质 | 营业执照 | `营业执照[_正副本]_到期日` |
| 资质 | 资质证书 / 体系认证 / 信用证书 / 其他 | `关键字_到期日` |
| 人员 | 注册证书 | `注册证书名关键字_注册有效期_使用有效期到期日` |
| 人员 | 岗位证书 | `关键字_到期日` |
| 人员 | 职称证书 | `职称等级关键字_专业` |
| 人员 | 身份证 | `身份证_国徽面|人像面_到期日` |
| 人员 | 毕业证 | `毕业证_专业` |
| 人员 | 个人荣誉 | `关键字_颁发日期` |
| 人员 | 简历 | `简历_上传日期` |
| 人员 | 退休证 | `退休证[_关键字]_长期` |
| 人员 | 返聘协议 | `返聘协议[_关键字]_到期日` |
| 业绩 | 项目文件夹 | `项目全名关键字_签订日期_总监`（无总监填 `无总监`） |
| 业绩 | 文件 | `文档类型_P0/P1` |
| 荣誉 | 荣誉证书 | `关键字_颁发日期` |
| 财务 | 财务证照 | `关键字_到期日` |

**动态扩展**：新增大类沿用通用式 `关键字_日期`；`scripts/bidcraft_naming.py` 的 `RULES` 表加一行即可支持专属字段。

### 分类口径（重要，防误归类）

- **荣誉大类 = 企业荣誉**：企业获得的荣誉称号——示范工程、标准化工地、文明工地、先进单位、AAA 级、重合同守信用等。
- **个人荣誉归 `人员/<姓名>/个人荣誉/`**：优秀 XX 工程师/总监/监理员、先进工作者、劳动模范等**给到个人**的荣誉，按持证人归入对应人员名下，**不得**放入荣誉大类。
- 脚本 `classify` 已按此口径区分（个人荣誉→人员/个人荣誉，企业荣誉→荣誉/荣誉证书）；归档时 agent 仍应结合图片内容确认，误判则以本口径修正。

### 人员目录内命名（命名不再带姓名）

`人员/<姓名>/<子类>/` 目录已确认归属，**文件名不再重复姓名**，只保留证书类型/关键字_日期（或按该子类命名规则）：
- `人员/阮旭/岗位证书/监理员_20280129.png`（而非 `监理员阮旭_…`）
- `人员/陈友龙/注册证书/监理工程师_20270623_20270308.png`
- `人员/吴志水/职称证书/工程师_给排水_P0.png`
- `人员/陈友龙/个人荣誉/优秀总监理工程师_20250101.png`

> 归档时 `keywords` 也不必含姓名（姓名由目录与台账 `person` 字段体现）；仅当子类文件本身以人名为核心（如个人简历）时例外。

## 六、台账字段

`<企业>/素材台账.csv` 与 `素材台账.json`（同内容，双份便于人读机读）：

| 字段 | 说明 |
|------|------|
| `id` | 8 位短 id |
| `category` / `subtype` | 大类 / 子类 |
| `rel_path` | 相对企业目录的路径（正斜杠） |
| `keywords` / `dates` | 提取到的关键字 / 日期（多个用「、」分隔） |
| `date_type` | 到期日 / 颁发日期 / 上传日期 |
| `owner` | 归属企业 |
| `upload_date` | 归档日期 |
| `original_filename` | 收件箱里的原始文件名 |
| `source` | 来源（收件箱） |
| `group_id` / `page_index` | 多页分组 / 页码 |
| `ext` | 扩展名（保持原格式，不转换） |
| `added_at` | 登记时间 |

检索示例：

```bash
python bidcraft.py query --category 人员 --keyword 监理工程师
python bidcraft.py query --expires-before 20270101          # 2027-01-01 前到期
python bidcraft.py query --category 资质 --json
```

## 七、回收站与 30 天清理

- 删除 / 被覆盖的文件移入 `<企业>/回收站/`，并登记 `_回收站清单.json`（含 `deleted_at` / `expire_at`）。
- **自动清理时机**：每次 `init-enterprise` 与 `open-inbox` 时顺带执行；也可手动：

```bash
python bidcraft.py cleanup-trash --days 30     # 或 --days 0 立即清空
```

## 八、企业归属校验

优先级：**文件名 → 文档正文 → 图像 OCR**。

- 文件名层：脚本自动完成（`inspect` / `propose` 内含）。
- 正文 / OCR 层：agent 用自身多模态能力读出企业名，再调用：

```bash
python bidcraft.py ownership-check --name "扫描件001.jpg" --text "从正文或图片识别出的文字…"
```

判定结果：`match` 与本企业相符 / `conflict` 疑似属于其他企业（会被提示）/ `unknown` 无法判定。

## 九、agent 对话检查点（务必落到人）

1. 无企业时 → 问企业全名。
2. `inspect` 出问题清单 → 逐条问「删除重传 / 保留归档」。
3. `propose` 后 → 把建议表给用户核对，特别是 `needs_input` 非空的条目（缺人员姓名 / 缺项目文件夹 / 缺日期）。
4. 多页归组 → 让用户圈选同组与先后。
5. 同名冲突（`is_name_conflict=true`，判定标准：**同大类 + 同子类 + 关键字相同**）→ 让用户选「并存 / 覆盖 / 跳过」，**确认前不得 `apply`**（脚本会拒绝并给出提示）。
6. 归属冲突 → 让用户确认是否放错企业。

---

## 九之二、归档后保护规则（硬性）

**素材一旦归档（`apply` 成功、已写入台账），即视为受保护**：
- 任何**更改、改名、移动、删除、覆盖、替换**，**必须走标准流程**（`propose` → 用户确认 → `apply`；或 `trash` 进回收站；或重走归档流程），**不得绕过脚本直接改文件系统**。
- 脚本只做确定性操作；agent 不得直接改文件、目录或台账。
- **例外**：用户**明确给出修改指令**时，才可按指令执行，并仍尽量走流程留痕。

## 十、已知边界与后续增强

- 归属校验的「正文/OCR」依赖 agent 能力，脚本只做文件名层；若 agent 未提供文本，结果为 `unknown`，不会误判。
- `group_hint` 只是弱启发，多页分组**必须人工确认**。
- 收件箱「同秒写入」无法自动定序，会主动提示。
- 后续可加：企业画像（M3）、素材完整性体检（缺哪类资质）、与 M5/M6 的素材自动调取接口。
