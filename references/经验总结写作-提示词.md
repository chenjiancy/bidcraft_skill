# 经验总结写作提示词（通用 · v1.1）

> **定位**：本文件是一个**可复用的写作提示词（prompt）**，不是某篇具体的总结。
> 当用户提出写「经验总结 / 复盘 / 阶段性总结 / 论文总结经验 / postmortem / 项目回顾」等诉求时，agent **必须先读取本文件，严格遵循其流程与质量标准，再动笔**（SKILL.md 索引同步此触发规则）。
> **目的**：把零散的开发日志沉淀为**有证据、可复用、能改进**的结构化总结，系统性提升写作质量，杜绝流水账与空话。
> **产出约定（v1.1）**：每次写经验总结，**必须产出 PDF 版**——「专业性版本」与「大白话版本」各一份 PDF（正文落位 `dev/notes/`，见 §七）；两份都须多带实例、对专业名词详细解释。
>
> **设计依据**（融合自联网查证的高质量框架）：4D 复盘法（Define/Discover/Decide/Deploy，敏捷回顾）、Post-Mortem 模板（Summary/What went well/What went wrong/Conclusion，强调证据+无指责）、研发四段式（结论→量化→踩坑→改进）、5 Whys 根因分析法、Google SRE Blameless 原则（复盘不追责个人、只修系统）、AWS 5 Whys 实操指南（每步带证据、允许多因分支、证据不足显式标注）、「成绩→做法→经验」三层提炼法（成绩=做成了什么；做法=具体干了什么；经验=为什么这样干能干成——必须答清「原来难在哪 / 改了哪个关键环节 / 换环境怎么照着做」）。

---

## 一、何时使用

用户提出以下任一类诉求时调用本提示词：写经验总结 / 复盘 / 阶段性总结 / 论文总结经验 / postmortem / 项目回顾。

---

## 二、动手前先取证（绝不凭记忆写）

1. 通读 `dev/notes/development-log.md`——本项目的原始素材，含「背景 / 决策 / 踩坑 / 验证 / 耗时」条目，是总结的事实底座。
2. 拉取事实：`git log --oneline` 看里程碑与时间线；按需读对应 `references/*-需求对齐.md`、`*-操作手册.md`。
3. 取量化证据：跑三塔层测试拿真实用例数
   `python -m unittest discover -s tests/unit -t .` 等；
   引用 CI 状态、版本号（`VERSION` / git tag）、日志中记录的真实耗时。
4. 素材不足时，**向用户索要缺失数据，不编造、不估算冒充实测**（硬性：缺数据 = 明示缺数据，禁止用印象补）。

## 三、写作流程

1. **对齐范围**：先向用户复述「总结覆盖哪个时间段 / 哪些模块 / 单次粒度（按里程碑/按月/按模块显式选定）」，确认后再写（沿用本项目「需求复述对齐」铁律：先对齐 → 再建议 → 后执行）。
2. **抽取事实**：从日志中归类「做对了 / 踩坑了 / 改进了」，每条必须能回指具体日期与证据。
3. **逼出根因**：每个踩坑用「5 问法」追到**系统级**原因，不归咎个人；**每次「为什么」的回答必须带证据**（日志/日期/测试数据/CI 状态）；一条因果链追不下去或出现分叉时，**允许多因分支分析**（分别列出各分支及其证据）；证据不足时显式标注「未证实」并说明缺口，不得强行凑五问。
4. **三层提炼（v1.1）**：每条经验必须过「成绩→做法→经验」三关——
   - 成绩：做成了什么（量化结果）；
   - 做法：具体干了什么（关键动作）；
   - 经验：**为什么这样干能干成**——必须答清三问：①原来难在哪 / 旧办法为何没解决；②这次改了哪个关键环节；③换一个环境（新项目/别人接手）怎样才能照着做。
   只写"做了什么"而未答"为什么能干成"的条目，不算经验，退回重写。
5. **落到动作**：每条改进必须可落地、有验收标准、有验证方式（如何确认已落地）。
6. **成稿**：按第四节结构输出，两份 PDF（§七）。

## 四、推荐结构（4D 复盘法 × Post-Mortem 融合）

1. **结论与量化结果**
   - 一句话结论 + 「计划 / 实际」对比表：里程碑、交付模块数、测试用例数、CI 通过率、关键耗时。
2. **关键事件时间线（v1.1）**
   - 一张简表：`日期 | 事件 | 影响/决策`（取 development-log 日期条目 + git 里程碑），让演进一眼可溯；详细叙事仍见 §4.3。
3. **开发过程总结**
   - **按时间线 / 里程碑回顾开发脉络**：用 `dev/notes/development-log.md` 的日期条目与 `git log` 里程碑，串起「需求对齐 → 契约 → 落代码 → 测试 → 操作手册 → 回填」的演进；标注关键版本节点（如 v0.3 项目级化、v0.7 测试金字塔+CI、v0.8 M4 解析、v2.x 双通道机制）。
   - **固化所用方法论（不仅写「做了什么」，更要写「怎么做的」）**：七步开发套路、agent/脚本/用户三分工、需求复述对齐铁律、测试金字塔 + CI/CD、scripts/ 分包结构、数据隔离（素材库不入仓）、对话检查点。
   - **记录关键架构 / 决策演进**：如项目级化改造、双通道解析机制（规则引擎 vs agent 语义 + 差异逐项裁决）、解析确认闸门（HTML 展示）、内容校验铁律 D25 等——说明「为什么这样定」，而非只列结果。
   - **指出当前开发流程中的问题（流程级，非单点 bug）**：对照 `references/模块开发规范.md` 的七步套路与硬性约定，从 `development-log.md` 中提炼**反复出现的流程摩擦**——如需求变更未走冻结、实现先于测试、agent 绕过脚本直接改文件、手动重命名脚本易错、静默未落盘类回归、对话检查点被跳过。要说明「流程哪一步松了 / 为什么会发生」，而不只是罗列现象。
   - **给出可复现的改进建议**：每条建议必须指向「**下次新项目如何照此流程复现且少踩坑**」——把已验证套路固化为 checklist / 脚本 / 模板，把对话检查点脚本化，用 CI 卡点拦截典型错误，把踩坑回写 `模块开发规范.md`。目标：流程**可复制、可教学、可交接**，而不是依赖个人临场发挥。
4. **做对了什么（Continue）**
   - 每条：做法 → 为什么有效（附证据，如测试覆盖率、复现脚本、回归数据）→ 下次如何复刻；并完成 §三.4 的三层提炼。
5. **踩坑与根因（Discontinue）**
   - 每条：现象 → 5 问法根因（带证据、允许多因分支、未证实显式标注）→ 当时解法 → 下次如何避免；
   - 诚实写出意外或「不舒服」的事实，不粉饰。
6. **改进动作（Deploy）**
   - 表格：动作 | 优先级(P0/P1/P2) | 验收标准 | **验证方式（如何确认已落地，v1.1）** | 状态。

## 五、高质量硬标准（交付前逐条自检，评分制 v1.1）

**评分规则**：每条按 0-2 分自评（0=未达标 / 1=部分达标 / 2=达标），交付时附自评表（每条分数 + 未达标项的说明 + 总分），由用户复核；两版（专业/大白话）分开自评。

- [ ] (2分) 每个判断都有数据或具体事例支撑，无「效率更高了」「基本完成」类空话。
- [ ] (2分) 含「开发过程总结」：体现方法论、里程碑演进与关键决策脉络（怎么做的），而非仅罗列成果。
- [ ] (2分) 开发过程总结中**指出当前流程的问题**（对照开发规范找流程级摩擦，非单点 bug）并**给出可复现的改进建议**（固化为 check-list/脚本/模板、CI 卡点等，使流程可复制）。
- [ ] (2分) **双版本均产出 PDF**：专业性版本 + 大白话版本，两份基于同一份取证、同一结构。
- [ ] (2分) 两版都**多带实例**：每条观点配 development-log 具体事件 + 日期 + 数据，禁止空对空。
- [ ] (2分) 两版都**对专业名词详细解释**：大白话版逐词用比喻/白话解释；专业版对易混/项目特有术语加一句说明。
- [ ] (2分) 至少 3 条「做对了」+ 3 条「踩坑」，且每条带证据。
- [ ] (2分) 识别出 ≥2 个**系统性模式**（非孤立事件），如「Windows BOM/编码」「Word 占位符跨 run 替换」「台账单源」类问题。
- [ ] (2分) 每条经验完成**三层提炼**（成绩→做法→经验；经验必须答清「原来难在哪/改了哪个关键环节/换环境怎么照做」，v1.1）。
- [ ] (2分) 每条踩坑的 5 Whys **每步带证据**；因果链分叉时做多因分支；证据不足处显式标「未证实」（v1.1）。
- [ ] (2分) 每条经验都产出具体、可验证的改进动作（有优先级/验收标准/**验证方式**）。
- [ ] (2分) 无指责个人语言，系统归因（「系统允许了 X」而非「某人弄错」）。
- [ ] (2分) 量化数据真实取自日志/测试/CI，非估算。
- [ ] (2分) 篇幅聚焦「坑 + 根因 + 改进」，不写过程流水账。
- [ ] (2分) 含「关键事件时间线」简表（日期|事件|影响，v1.1）。

## 六、反例（必须避免） vs 正例

- ✗ "本次开发总体顺利，积累了不少经验。"（无信息量）
- ✗ "Word 模板处理比较坑。"（无根因、无证据）
- ✓ "Word 生成器首次实战因招标原文 `sectPr` 内**悬空 footerReference**（rId 在新 rels 中不存在）导致四分之一分段判定损坏，四轮诊断 3.5h 定位；改进：M7 新增 `word_open` 冒烟项常态化校验（见 development-log 2026-10-04）。"
- ✗ "我们做了双通道解析。"（只写做法，未答为什么能干成）
- ✓ "双通道解析能落地，关键是把'确定性字段'交给规则引擎、把'开放性语义'交给 agent——原来单靠规则引擎会漏评分细则、单靠 agent 会编页码，两者互补 + 差异逐项交用户裁决，才做到既快又不失真（见 development-log 2026-10-07）。"（完成三层提炼）

## 七、双版本产出（每次必须产出两个 PDF）

每次写经验总结，必须同时产出**专业性版本**与**大白话版本**（PDF），二者基于同一份取证、同一套结构（第四节），但受众与写法不同：

- **专业性版本**（`dev/notes/经验总结-<时间段>-专业版.pdf`，草稿 md 同名保留）：面向同行 / 技术评审 / 日后自己深挖。保留必要术语，结构严谨，密集引用证据（development-log 日期、git 里程碑、测试用例数、CI 状态、版本号）。适合归档、复盘、交接。
- **大白话版本**（`dev/notes/经验总结-<时间段>-大白话版.pdf`，草稿 md 同名保留）：面向非技术读者 / 自己日后速读。用生活化比喻讲清「在做什么、卡在哪、怎么改」，少 jargon、多故事化；**每个专业名词首次出现必须用括号/脚注详细解释**。

**两版通用硬要求**：
1. **多带实例**：每条观点（做对了 / 踩坑 / 流程问题 / 改进）都配 development-log 中的具体事件 + 日期 + 数据，禁止空对空。
2. **专业名词详细解释**：
   - 大白话版：逐词解释，用比喻降低门槛。例：「双通道解析」→ 就像让两个人独立看同一份招标文件，一个按死规则抠数字（规则引擎），一个凭理解抓重点（agent 语义），再比对两人结果，不一致的交你拍板。
   - 专业版：对易混 / 本项目特有术语也加一句简要说明。例：「D25 内容校验铁律」「sectPr 内悬空 footerReference（段落属性里指向了不存在的页脚引用，导致 Word 判损坏）」。
3. 两份都在回复中说明文件位置与差异，并给出各自的核心结论与改进清单。
4. 语言：中文、简洁、对事不对人。
5. **PDF 交付**：以 md 草稿为源，用 word/pdf 技能转 PDF；交付时经 present_files 提供 PDF（草稿 md 一并保留在 dev/notes/ 便于追溯）。

## 八、Golden 样例与变更回归（v1.1）

- **Golden 基准**：本提示词产出的**第一篇经用户认可的经验总结**即沉淀为 Golden 样例（`dev/notes/golden-经验总结-<时间段>.md/pdf`），作为后续输出的质量基准。
- **变更回归**：任何人（含 agent 自行优化）改动本提示词前，先跑一遍 Golden 样例按新提示词重写，对比新旧输出质量（结构完整度 / 证据密度 / 三层提炼达成 / 自评得分），确认不退化后才允许定稿；变更记入下表并保留旧版本可回滚。
- 与 M4 招标文件解析提示词、Golden 测试集（tests/fixtures/m4_golden）同一治理思路：**提示词是资产，版本化 + 回归 + 可回滚**。
