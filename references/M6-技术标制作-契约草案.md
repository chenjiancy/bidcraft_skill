## 一、目标与边界

### 1.1 目标

在 M4 解析产物基础上，生成**技术标（监理大纲/技术方案）**正文：按评分项组织章节、按招标格式要求控制篇幅、按企业可复用素材注入事实、按写作风格成文，并产出可交付 docx 与可被 M7/M8 消费的结构化产物。

### 1.2 明确不做（本期）

| 不做 | 原因/归属 |
|---|---|
| 深度排版美化、去 AI 味、页数硬达标 | 属外部专项技能（`bid-service-plan-markup-docx`），调用点在契约 §9 显式声明；**内置预设见 §3.2（D8）** |
| 模拟评分 | 归 M8（M6 只提供文本 + 章节结构，供 M8 主观分评审） |
| 合规/废标审查 | 归 M7（M6 只做写作侧自检：覆盖度/篇幅/暗标/术语一致） |
| 自动补造业绩、人员、证书 | 铁律：素材未列不生成（延续 M5 范式） |
| 知识库检索实现 | 归 M3（M6 仅预留读取接口，M3 未交付时不阻塞，见 D7） |

> **D8 裁决（2026-10-21）**：不建 M2 技术标 docx 母版，改为 **M6 内置排版预设引擎**——版面范式 7 种 × 配色方案 11 种 × 封面版式 4 种 × 装饰强度 3 种。预设负责结构与视觉样式套用（标题层级、表格样式、分栏、封面色块、页眉页脚），不做字体级精雕；深度美化仍可交外部技能二次加工。详见 §3.2。

### 1.3 关键定位（与 M5 的差异，必须说清）

M5 商务标 = **确定性填充**（模板母版 + 素材清单，脚本执行，AI 不参与）。
M6 技术标 = **语义生成**（章节内容必须由 agent 写，脚本只做上下文供给、结构校验、落盘与检查）。

因此 M6 **不照搬 M5 的 fill-tpl 范式**，而是照搬 M4/M7 的**双通道范式**：

- 通道A（脚本，确定性）：章节树结构校验、评分点覆盖矩阵、篇幅核算、暗标敏感词扫描、术语/人员一致性、写作状态机、docx 合并与导出。
- 通道B（agent，语义）：目录编制、章节正文写作、精修。
- 通道间：`tech-check` 出机器结论，`tech-diff` 列差异，**逐项人工裁决**（同 M4 v2.4 纪律）。

## 二、目录与产物契约

### 2.1 落位

项目级，与 `招标解析/`、`商务标\`、`标书检查\`、`模拟评标\` 同级：

```
<软件根>/<企业>/项目级/<项目名>/技术标/
├── 章节树.json                  # 核心调度中枢（章节 + 评分点映射 + 状态）
├── 章节树.md                    # 人读版（闸门①展示辅助）
├── 章节/
│   ├── ch-01.md                # 章节正文（agent 产出，可人工直改）
│   ├── ch-01.docx              # 可选：单章导出（便于交付分段审阅）
│   └── .meta/
│       ├── ch-01.json          # 上下文包（喂给 agent 的裁剪素材，可审计）
│       └── ch-01.state.json    # 状态机（PENDING/WRITING/WRITTEN/CHECKED/CONFIRMED/FAILED）
├── 检查/
│   ├── 覆盖矩阵_<项目>.json/.md # 通道A：评分点 × 章节 覆盖 + 篇幅核算 + 硬问题
│   ├── 写作统计_<项目>.json     # 字数/表格数/图表占位统计，按章
│   └── 技术标检查报告_<项目>.html # 人工确认闸门②
├── 产出/
│   ├── 技术标_<项目>.docx       # 合并终稿（含目录域）
│   └── 技术标_<项目>.md         # 合并 md（审阅用）
└── 源文件/                      # 招标技术标格式要求摘录（引用 M4 响应文件格式文件，不重复拷贝）
```

### 2.2 为什么 `章节树.json` 是中枢

对齐原项目"目录即状态"的设计（`目录/05-目录最终.json`）：章节编号（dewey 风格 `1` / `1.1` / `1.1.1`）、评分点映射、字数预算、状态、文件路径全部集中一处，脚本按它调度、agent 按它写作、M8 按它定位文本。

### 2.3 `章节树.json` 结构（契约固定）

```json
{
  "schema": "m6.chapters/v1",
  "project": "项目名",
  "bidMode": "明标",
  "pageConstraint": {"max": 80, "estimate": 72, "charsPerPage": 900, "source": "招标文件 第X章 响应文件格式"},
  "style": {"id": "strict", "name": "严谨正式", "promptRef": "styles.json#strict"},
  "layout": {"preset": "single-column", "palette": "deep-indigo", "cover": "full-block", "decoration": "standard"},
  "terminology": {"招标人": "...", "项目名称": "...", "服务期": "..."},
  "personnel": [{"name": "张三", "post": "总监理工程师", "source": "素材清单#personnel[0]"}],
  "chapters": [
    {
      "id": "ch-01", "no": "1", "title": "工程概况与监理工作范围", "level": 1,
      "scoreRefs": [{"idx": 3, "item": "监理大纲（30分）", "weight": 30}],
      "keyPoints": ["...", "..."],
      "wordCnt": 3000,
      "dependsOnMaterials": ["project_overview", "personnel"],
      "status": "PENDING",
      "files": {"body": "章节/ch-01.md", "meta": "章节/.meta/ch-01.json"}
    }
  ]
}
```

**强制字段**：`id/no/title/level/scoreRefs/keyPoints/wordCnt/status/files`，以及顶层 `layout`（五组预设 id，见 §3.2）。
**禁止字段**：任何由脚本填充的统计值（字数、页数）不得由 agent 写入——脚本回填。

## 三、输入契约（字段级）

### 3.1 数据来源

| 来源 | 取什么 | 用途 | 缺失时行为 |
|---|---|---|---|
| M4 `投标要点_<项目>.json` → `modules[scoring].score_items` | 逐条 `{item, weight, evidence}`；脚本按 M8 同款规则表分型（`outline` 为主观分项） | 章节树必须逐条覆盖 `outline` 项；`keyPoints` 从 item 原文拆 | **硬阻断**：无 scoring 或无 score_items → 拒绝 `tech-outline`（对齐 M8 报错语义） |
| M4 `modules[project_overview]` | 改造范围/栋数户数/规模/监理工作内容与范围/监理依据与目标 | 技术标写作的事实底座（P3 注入） | 缺失 → `tech-outline` 标 warn，章节树可生成但正文写入「待补」 |
| M4 `modules[reject]` | 废标红线（尤其"技术标不得出现XX""页数超限"） | 暗标规则、敏感词表来源 | 缺失 → 使用内置默认敏感词表 |
| M4 `modules[submission]` | 份数/装订/递交（摘要） | 不用于正文，仅报告展示 | 可缺 |
| M4 `响应文件格式_<项目>.txt` | 技术标章节格式要求、页数上限、装订/字体要求 | 章节树骨架依据之一 + 页数约束抽取 | 缺失 → 章节树改由评分项 + 默认骨架生成（标 warn） |
| M4 `素材清单_<项目>.json` → `personnel` | 拟派人员（姓名/岗位/证书） | **技术标人员唯一来源**（防与商务标附表7不一致） | 缺失 → 正文只写岗位不写姓名，标缺料披露 |
| M1 `query()` | 组织架构、企业简介、类似业绩（可选注入） | 章节中的企业实力段 | 未命中 → 不生成该段，披露 |
| M2 模板库 | **不使用**（D8 裁决：建内置预设，不建技术标母版） | — | — |
| 共享级 `layout-presets.json` | 排版预设：版面范式 / 配色 / 封面 / 装饰强度 / 字体方案 / 图文比例 / 配图规则 / 配图排版 | `tech-export` 套用 docx 样式 | 缺失 → 用内置 `default` 组合 |
| M3 知识库 | 法规/规范条文（**接口预留**，见 D7） | 引用规范条文 | M3 未交付 → prompt 中禁止引用具体条文编号，只允许"依据现行监理规范"类表述 |
| 共享级 `styles.json` | 写作风格 `{id, name, prompt, require}` | 注入 P3 system 段 | 缺失 → 用内置 `default` 风格 |

**跨模块一致性铁律**：
1. 人员姓名/岗位一律取素材清单，技术标不得自造人名；
2. 项目名称/招标人/服务期取 `terminology`（由 M4 投标要点回填），各章表述一致；
3. 业绩引用必须能在素材库台账命中，不得虚构金额/时间。

**D2 裁决（2026-10-21）：章节树生成依据 = 评分项优先**——`score_items` 决定章节骨架与权重，招标"响应文件格式"作为**约束校验**（若格式文件明确规定了章节顺序/固定条目，`tech-outline` 必须校验并提示"未满足格式要求"），默认骨架仅作兜底补位。

### 3.2 排版预设引擎（D8 裁决，内置不建母版）

**落位**：共享级 `<软件根>/共享资源/技术标风格/layout-presets.json`（与 `styles.json` 同目录）。
**可增行表原则**：五组预设均为数组，增删一项不改代码。

#### ① 版面范式（7 种）

| id | 名称 | docx 实现要点 |
|---|---|---|
| `single-column` | 单栏流式 | 默认：标题层级 + 段落流 |
| `tabular` | 表格化布局 | 关键内容（人员/进度/设备/指标）强制转表格；正文段落保留 |
| `two-column` | 双栏分栏 | section `sectPr` 设 `w:cols`；仅正文段分栏，标题跨栏 |
| `card` | 卡片式布局 | 单元格底纹 + 边框模拟卡片（docx 无圆角）；每卡一个要点 |
| `image-left` | 左图右文 | 两列表格：左图占位 + 右文；图缺失则降级单栏并披露 |
| `divider` | 章节分隔页 | 每章前分页 + 大号章号/章名页；页眉不显示章名 |
| `data-row` | 数据行布局 | 指标横排（KPI 行）→ 表格化，适合工期/人数/面积等数据章 |

#### ② 配色方案（11 种）

`深靛蓝 / 暖棕金 / 松绿 / 砖红 / 钢青 / 炭灰极简 / 深海蓝金 / 墨绿暖橙 / 茄子紫银灰 / 黑白灰一点红 / 渐变蓝青`

每套配色定义 5 组色值（`primary / accent / heading / tableFill / coverBg`）。**色值已于 T13 经用户确认并固化**（2026-10-21，见 `共享资源/技术标风格/layout-presets.json` 与 `色卡预览.html`）。
「渐变蓝青」在 docx 中以**两段色块拼接**近似渐变（python-docx 不支持原生渐变填充，`coverBgEnd=#2A8BA8`）。

#### ③ 封面版式（4 种）

| id | 名称 | 实现要点 |
|---|---|---|
| `full-block` | 满版色块 | 整页底色块 + 标题反白 |
| `line-white` | 留白线条 | 白底 + 细线框/分隔线 |
| `image-underlay` | 图底压字 | 背景图 + 标题叠压（暗标时禁用，避免图片泄露信息） |
| `gradient` | 渐变 | 两段色块近似 |

#### ④ 装饰强度（3 种）

`克制 / 标准 / 丰富` —— 控制装饰元素密度：克制=仅标题色 + 细线；标准=标题色块 + 表头底纹；丰富=章首装饰带 + 图标 + 强调底色。

#### ⑤ 字体方案（5 种，v0.6 新增，2026-10-22 用户确认）

| id | 名称 | 标题 / 正文 / 西文 | 字号骨架（章→节→条→正文→表格→图表注） | 行距 | 暗标 |
|---|---|---|---|---|---|
| `gov-gongwen` | 政务公文风 | 黑体 / 仿宋 / Times New Roman | 16→14→12→12→10.5→9pt（章居中） | 1.5 | 禁用，强制 `dark-safe` |
| `engineering` | 工程务实风 | 黑体 / 宋体 / Times New Roman | 同上 | 1.5 | 禁用，强制 `dark-safe` |
| `modern-business` | 现代商务风 | 微软雅黑（加粗）/ 微软雅黑 / Calibri/Arial | 16→14→12→12→10.5→9pt | 1.4 | 禁用，强制 `dark-safe`（字重偏粗） |
| `elegant-classic` | 典雅书卷风 | 华文中宋 / 楷体 / Georgia/TNR | 16→14→12→12→10.5→9pt（条标题加粗） | 1.5 | 禁用，强制 `dark-safe` |
| `dark-safe` | 暗标安全风 | 宋体 四号常规 / 同左 / 同正文 | 全部 14pt 四号常规；表格 10.5pt 五号常规 | 1.5（济南条款=固定 25 磅） | **本体**，`bidMode=暗标` 时强制 |

**要点**：全黑统一、禁加粗/斜体/下划线/加色、不设封面/页眉页脚/页码；变体——招标点名"仿宋_GB2312 小四"（如南通监理条款）时按条款切换并确认本机字体存在（Win10/11 无 GB2312 版本，缺失回退"仿宋"）。楷体/仿宋篇幅约 +5%，页数预算以 `tech-export` 实测回写为准（R1 同源）。每套含 `heading/body/western/sizes/lineSpacing/system/darkOk/note` 字段，存于 `layout-presets.json#fontSchemes`。

#### ⑥ 配图规范（v0.7 新增，2026-10-22 用户确认）

三组可增行表：**图文比例 imageRatio（4 档）× 配图规则 imageRule（5 套）× 配图排版 imageLayout（5 套）**，组合数 4620 × 4 × 5 × 5。

| 组 | id | 说明 |
|---|---|---|
| 图文比例 | `none` 无图 0:10 | **零图模式**：不生成/不插入任何图表，纯文字；暗标推荐（切断人脸/品牌/水印/版权全部图片风险）；tech-export 跳过图片、image-left 降级单栏、页数按纯文字折算 |
| | `low` 低图比 1:9 | 图占版心≈10%；理论密集型章节（质量/进度/投资控制、监理程序） |
| | `mid` 中图比 3:7 | **默认**；图占版心≈30%；现场照片每页≤2 张（行业口径） |
| | `high` 高图比 5:5 | 图占版心≈50%；图证型章节（现场平面布置/安全文明施工/样板引路）；流程图每页 1 张；暗标须转灰度+附图专页 |
| 配图规则 | `upload-first` 上传优先 | 人工上传图（存量少）只放关键证据位（业绩/资质/人员/荣誉）；仅等比缩放+质量检查 |
| | `search-supplement` 搜索补图 | 联网搜真实工程场景图；短边≥600px、无水印优先、尽量无人脸/品牌；标"示意图"；版权风险高（国家版权局 2020 通知），不用于事实陈述 |
| | `ai-render` AI 生图 | 工程场景示意图作主力：统一画风、无版权、可控（指定无人脸/无文字标识/无品牌）；嵌入 docx 前重编码标准 JPEG |
| | `hybrid` 混合策略 | **默认**；关键证据→上传图，真实场景→搜索图，风格补全→AI 图；三源混排时边框/色调统一 |
| | `dark-safe-img` 暗标安全 | 无论来源一律过安全闸：转灰度/黑白、人脸不可辨识、招牌/品牌/文字遮盖、EXIF 与文件名清洗 |
| 配图排版 | `split-h` 左右分栏 | **默认**；左图右文/左文右图，两列表格承载；图不跨栏不折行 |
| | `split-v` 上下分栏 | 上图下文：横图+图注+正文段落 |
| | `inline` 图文混排 | 图嵌段落中文字环绕，小图穿插正文 |
| | `grid` 图组并排 | 2 张同尺寸图并排+组注；前后对照/多工序对比 |
| | `appendix` 附图专页 | 图集中章节末/文末附表，正文"见附图 X"引用；**暗标强制**（青海/安庆检测规则：附图依次附于标书最后） |

**暗标图片硬约束（废标级，源自真实招标条款）**：图片图表须黑白/灰度、人脸打成不可辨识阴影、商户/品牌/招牌信息遮盖、图表内文字五号宋体黑字常规无涂色着重号下划线；正文不得插入图表、附图附表依次附于标书最后（青海/安庆）。**暗标二选一（校验 error）**：`imageRatio=none`（零图），或 `imageRatio≠none` 时须同时 `imageRule=dark-safe-img` 且 `imageLayout=appendix`。

#### ⑦ 章节树记录方式

`章节树.json` 增加：

```json
"layout": {"preset": "single-column", "palette": "deep-indigo",
           "cover": "full-block", "decoration": "standard",
           "font": "gov-gongwen",
           "imageRatio": "mid", "imageRule": "hybrid", "imageLayout": "split-h",
           "overrides": {"headingFont": "仿宋", "bodyFont": "仿宋"}}
```

**约束**：
1. 预设 id 必须在 `layout-presets.json` 中存在，`tech-outline` 校验失败即报错；
2. `bidMode=暗标` 时强制 `cover!="image-underlay"`、`font=="dark-safe"`、图片二选一（`imageRatio=none` 或 `dark-safe-img+appendix`，校验 error），配色不得使用企业色（校验 warning）；
3. 字体默认 `gov-gongwen`（正文仿宋，沿用用户既有偏好），图文默认 `mid+hybrid+split-h`，暗标默认 `none`，可在 `overrides` 改具体字族；
4. 预设只影响 `tech-export`，不影响正文 md 内容——保证"内容与版式解耦"。

### 3.3 专家包（v0.8 新增，2026-10-22，R-T1/R-T2 已落地）

**定位**：专家包 = **可切换的"配置集"**（目录学 taxonomy + 版式组合 + 风格引用），**不含提示词正文**——提示词一律归 `styles.json` 与 M6 提示词 P2/P3/P5。灵感源自链企 Buddy「行业专家」体系逆向（见 `e:\链企Buddy分析\C6-expert-replication-map.md`）：链企在服务端把 expertGroupId 捆绑 taxonomy/版式/提示词；bidcraft 将其拆为本地可审计文件，提示词透明、可版本管理。

**落位**：共享级 `共享资源/技术标风格/专家包/<包id>/`，每包两文件：

```
共享资源/技术标风格/专家包/
└── official-tech/            # 首个包：官方技术标专家包（施工类，链企官方团 id=1 镜像）
    ├── 包.json               # 包清单（schema: m6.expert-pack/v1）
    └── taxonomy.json         # 13 类章节分类体系（schema: m6.taxonomy/v1）
```

**`包.json` 字段**：`schema / id / name / description / tags[] / bidType[] / docType / taxonomy（文件相对路径）/ layoutCombo（8 个预设 id，均须存在于 layout-presets.json）/ styleRef（styles.json#id）/ source（镜像溯源：kind/expertGroupId/capturedAt/evidence）`。
**`taxonomy.json` 字段**：`schema / pack / docType / classes[]`，每类 `{id, name, description（写作要点）, bodyMode, illustration}`；**不含 contentPromptDataId**（服务端提示词引用，正文客户端不可得，剔除）。

**接线（R-T3 实现）**：
1. `tech-outline --expert-pack <id>`：有包 → 其 taxonomy 作 P2-R3 兜底骨架来源（类目 name 作章名、description 注入对应章 `.meta` 上下文包）；无包 → 现状不变；
2. `章节树.json` 增 `expertPack` 字段（记录包 id，对齐 `layout` 五组字段写法）；
3. 校验：包 id/layoutCombo 各 id 必须存在，缺失即报错（**不静默兜底**——对齐链企 C5-2 教训的反面）；
4. `styles.json`（T6）交付后，`styleRef` 生效；未交付时忽略 styleRef 并披露。

**首包 provenance**：链企官方团 1（`resolvedGroupId:1`，自有 13 类无回落），镜像自 `expert-kit-export/taxonomy/1-ENGINEERING.json`（2026-10-22 实抓）。`bodyMode:"two_step"` 与 M6 P2→P3 两步范式互证。

## 五、流程与闸门（四闸门）

```
① tech-init（建目录 + 校验 M4 产物就绪）
    ↓
② 通道B：agent 按 M6 提示词 P2 编章节树 → tech-outline 脚本结构校验（覆盖度/编号连续性/字数预算）
    ↓  【闸门①：章节树人工确认】← tech-report 展示覆盖矩阵，逐项确认
③ tech-ctx：逐章生成上下文包（.meta）
    ↓
④ 通道B：agent 按 P3 逐章写作 → tech-parse 落盘（状态机推进）
    ↓
⑤ tech-check（通道A 机器检查）→ 硬问题清单
    ↓  【闸门②：写作结果人工确认】← HTML 报告，缺料/覆盖缺口逐项裁决
⑥ 人工精修（Word 或 md 直改）→ tech-rewrite（可选，agent 基于现有文本改）→ 差异披露
    ↓
⑦ tech-export（合并 + docx + TOC 刷新）
    ↓  【闸门③：终稿确认】→ 交付；后续接 M7 check-rule / M8 eval-parse
```

**闸门纪律（对齐 M4 v2.4/v2.5）**：
- 闸门①未确认 → 禁止 `tech-ctx`/`tech-parse`（程序化强制：`章节树.json` 无 `confirmed: true` 且无 `confirmLog` → 拒绝）；
- 闸门②存在 `error` 级问题时 → 禁止 `tech-export`（除非用户显式 `--force` 并记录）；
- 所有裁决结果落 `章节树.json.confirmLog`，不静默跳过。

## 六、双通道设计

### 6.1 通道A（脚本，确定性）—— `tech-check` 六项

| # | 检查项 | 规则 | 级别 |
|---|---|---|---|
| A1 | **评分点覆盖** | `score_items` 中 `kind=outline`（及用户指定）每一项，必须至少被一个章节 `scoreRefs` 引用；`keyPoints` 与该 item 原文有交集词 | error |
| A2 | **章节编号连续性** | dewey 编号合法、父章存在、无跳号/重号、层级 ≤3 | error |
| A3 | **篇幅核算** | Σ字数 ÷ `charsPerPage`（可增行表：正文 1000/页、表格 500/页，可配）vs `pageConstraint.max` | error（超限）/ warn（不足 60%） |
| A4 | **暗标敏感词** | `bidMode=暗标` 时扫描企业名/logo/商标/人名/联系方式（词表 = M4 废标红线 + 内置表 + 术语表反查） | error |
| A5 | **术语/人员一致性** | 术语表词条在各章表述一致（如"招标人"不得混用"甲方"）；人员姓名/岗位与素材清单一致 | warn |
| A6 | **占位/垃圾残留** | `{{待填` / `TODO` / `XXX` / 空格段落 / 未替换占位符 | warn（可批量定位） |

> 不做语义判断：A1 只做"引用存在 + 关键词交集"，语义是否真的覆盖由通道B/人工裁决。

### 6.2 通道B（agent，语义）—— 三个提示词

| 提示词 | 触发 | 依据 |
|---|---|---|
| P2 目录编制 | `tech-outline` 前 | `references/M6-技术标制作-提示词.md` 的 P2 段 |
| P3 单章写作 | 每章一次 | 同上 P3 段，注入上下文包 |
| P4 批量编排 | 批量写作时由 agent 自守 | 同上 P4 段（B1–B9 编排约束） |
| P5 精修 | `tech-rewrite` 时 | 同上 P5 段（定向修订 + `M6-REVISE` 变更块） |

提示词**已落地**：`references/M6-技术标制作-提示词.md` v1.0（2026-10-21，T2 完成）——P2 目录、P3 单章、P4 批量编排、P5 精修；改造点含：素材未列不生成、暗标口径（含 `personnelWriteMode`）、术语表注入、素材清单人员唯一来源、缺料披露 `{{待填}}`、知识库不可用时禁引条文号、自述覆盖块 `M6-COVERAGE`。

### 6.3 `tech-diff`（一期实施，D10 已裁）

通道A 覆盖矩阵 vs agent 自述覆盖 → 差异列示（对齐 `tender-diff`/`check-diff`），差异逐项交用户裁决并记入 `confirmLog`。

**自述载体**：P3 正文末尾的 `<!-- M6-COVERAGE {...} -->` 注释块，由 `tech-parse` 解析至 `章节/.meta/ch-xx.selfcheck.json` 后从正文剥离（见 `M6-技术标制作-提示词.md` v1.0「自述块解析约定」）。

对比维度：
1. **覆盖结论冲突**：A1 判定"未覆盖"但 agent 自述已覆盖（或反之）→ 人工裁决；
2. **篇幅偏差**：A3 估算与 agent 自述字数差 > 20% → 列示；
3. **仅通道B发现项**：agent 标注"招标要求模糊/疑义"而 A1 无结论 → 列示；
4. **仅通道A发现项**：机器命中但 agent 未提及（典型：暗标敏感词、占位残留）。

裁决纪律同 M4 v2.4：**不得静默判定"实质一致"后略过**。

## 八、三分工（硬性）

| 主体 | 职责 | 禁止 |
|---|---|---|
| 脚本 | 目录/落盘/结构校验/覆盖矩阵/篇幅核算/敏感词/状态机/合并导出 | 不得生成正文、不得判断"这章写得好不好" |
| agent | 编目录、写正文、精修、语义裁决建议 | 不得直接改文件系统（一律提交给 `tech-parse`）、不得编造素材 |
| 用户 | 闸门①章节树确认、闸门②写作结果裁决、闸门③终稿确认、缺料决策 | — |

**状态机**：`PENDING → CONTEXT_READY → WRITING → WRITTEN → CHECKED → CONFIRMED / FAILED`。
- `tech-ctx` 成功 → `CONTEXT_READY`
- `tech-parse` 成功 → `WRITTEN`
- `tech-check` 通过 → `CHECKED`
- 闸门② 用户确认 → `CONFIRMED`
- 异常/回读失败 → `FAILED`（保留现场，可重跑）

**批量纪律**（移植原项目踩坑结论，写入提示词 P4 + 操作手册）：
1. 每章独立会话，仅共享章节树/术语表/评分点原文；不注入其他章正文；
2. 术语表统一注入，保证称谓一致；
3. 失败续写：只处理非 `WRITTEN/CONFIRMED` 章；
4. **重写前旧正文先入 `.rewrite-trash/<时间戳>/`，失败可还原**；
5. 落盘遇 `EPERM/EACCES/EBUSY` 按 20/40/80/160/320ms 退避 5 次（Windows 文件锁常态）；
6. 并发上限默认 3（个人机 + 模型限速），可配。

## 十一、硬性约束（写入模块约定）

1. **不臆造**：材料没有的数据写 `{{待填:说明}}` 交人工；不得编造人名/业绩/金额/证书编号/规范条文号。

4. **单项目隔离**：所有输入输出路径必须在 `项目级/<本项目>/` 内。
5. **一切产出真实执行**：未跑脚本不得声称完成；回读失败必须报错暴露。
6. **闸门不静默**：三个闸门均需用户明确确认，确认记录落 `confirmLog`。
7. **可回滚**：重写正文前旧文件入 `.rewrite-trash/`；导出覆盖前旧 docx 入同目录 `.bak`。
8. **不读合同内容**：与 M4 一致，技术标不得引用合同条款（除用户明确要求）。

## 十四、风险与披露

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | 页数估算与实际排版偏差 | 字体/行距/表格密度决定真实页数，估算仅用于写作预算 | 终稿以外部排版技能实测为准；`tech-export` 后回写实测页数 |
| R2 | 技术标质量强依赖提示词与模型 | 章节"像不像投标文件"取决于 P3 措辞与所选模型 | Golden 样例 + 2~3 份真实标书调试；风格库可切换 |
| R3 | 评分点覆盖判定偏机械 | A1 靠关键词交集，可能误判"名义覆盖" | 保留通道B/人工裁决；覆盖矩阵标注"机器判定，须人工确认" |
| R4 | 暗标敏感词漏检 | 企业简称/项目别名可能不在词表 | 从 M4 术语表 + 素材库企业名自动派生词表；人工补充入口 |
| R5 | 长章一次生成质量下降 | 超 5000 字易跑题/重复 | D3-B 自动拆小节；P3 严格字数区间 |
| R6 | 与商务标人员不一致 | 两处人员名单不同步 | 人员唯一来源=素材清单；A5 一致性检查 |
| R7 | 排版预设的实现边界 | python-docx 不支持原生渐变/圆角/复杂分栏，需直接操作 OOXML；「渐变蓝青」「卡片式」需降级近似 | T13 先做样张验证，能力不足的预设降级并披露；不承诺像素级还原 |
| R8 | 封面版式与暗标冲突 | `image-underlay` 背景图可能泄露企业标识 | §3.2 已强制暗标禁用该预设；`tech-outline` 校验拦截 |
| R9 | 配色色值需用户确认 | 契约未定义具体色值，直接写死会偏离用户审美 | T13 出 11 套色卡预览，确认后固化进 `layout-presets.json` |
