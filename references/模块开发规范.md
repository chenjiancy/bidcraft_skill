# bidcraft 模块开发规范（M1 已验证，供 M2–M8 复用）

> 来源：M1 素材库的实现经验（2026-10-01）。后续每个模块按此套路开发，保证风格统一、可被任意 agent 驱动。

---

## 一、开发七个步骤

1. **需求对齐**（必做，不得跳）
   - 触发用户已有技能 `requirement-alignment`：结构化访谈 → 逐条确认 → 产出 `references/M<N>-<模块名>-需求对齐.md`。
   - 文档必须含：目标与形态、数据结构/目录、业务规则、**决策汇总表（编号+结论）**、待确认项（全部关闭后才定稿）、技术方案、任务拆解。
   - 用户确认后**冻结为 v1.0**；后续变更另开 v1.1 并写明原因。

2. **先定契约**：在 `references/module-contracts.md` 该模块条目补「输入 / 输出 / 依赖 / 状态 / 下一步」。

3. **三层落代码**（M1 验证有效的分层）
   | 层 | 职责 | 约束 |
   |----|------|------|
   | 纯逻辑层（如 `bidcraft_naming.py`） | 规则、算法、解析、校验 | **无 I/O**，可单元测试 |
   | 存储/编排层（如 `bidcraft_core.py`） | 文件系统、数据读写、状态机 | 只做确定性操作；**语义判断交给 agent** |
   | CLI 层（如 `bidcraft.py`） | argparse 子命令、人读表格 + `--json` 机读 | 全局参数 `--root / --enterprise / --json` |

4. **依赖最小化**：优先只用 **Python 标准库**，避免 venv 与安装成本；确需第三方再在项目内建 `.venv`（用户约定）。

5. **端到端冒烟测试**：写临时脚本跑通「建 → 传 → 处理 → 查 → 清理」全链路，逐命令核对退出码与产物；测完删脚本并清理临时目录。**未经测试不得标记交付。**

6. **写操作手册**：`references/M<N>-<模块名>-操作手册.md` —— 分工说明、标准流程、字段定义、命令速查、与用户的对话检查点。

7. **回填状态**：更新 `SKILL.md`（frontmatter version + 模块状态表 + 用法入口）与 `references/module-contracts.md`（状态 ✅ + 实现说明 + 下一步），并追加项目日志。

---

## 二、硬性约定（所有模块都必须遵守）

1. **agent / 脚本 / 用户三分工**
   - 脚本：确定性操作（建、改、移、算、查、记录）。
   - agent：语义判断（看懂内容、归类、抽取、比对、生成建议）。
   - 用户：决策（确认、选择、取舍）。
   - **禁止脚本假装懂语义，也禁止 agent 绕过脚本直接改文件系统。**

2. **一切产出必须来自真实执行**：脚本没跑就不许声称完成；报错如实转述，不美化。

3. **对话检查点不得静默跳过**：凡涉及「删除、覆盖、归类归属、多页分组、同名冲突」，必须落到用户确认。

4. **幂等与可回滚**：初始化类命令可重复执行；删除/覆盖一律进回收站，不物理删除。

5. **路径与编码**：路径用相对项目根书写，数据存正斜杠相对路径；文件读写显式 `encoding="utf-8"`，CSV 用 `utf-8-sig`；脚本对 stdout 做 UTF-8 reconfigure（Windows 控制台中文）。

6. **退出码语义统一**：`0` 成功 / `1` 参数或状态错误 / `2` 部分失败（附明细）。

7. **双份数据**：人读用 CSV/表格，机读用 JSON（或 `--json`），二者内容一致。

8. **可扩展优先**：分类、规则、模板一律做成**可增行的表**（如 `RULES` 字典），不写死流程分支。

9. **需求复述对齐（先对齐 → 再建议 → 后执行）**：用户提出需求后，agent **必须先复述需求**（目的：对齐双方需求理解），**用户确认后**再**联网查询权威知识与行业成熟经验**给出建议/方案，最后才执行。开发与测试同样遵循：任何改动先向用户披露，回归测试（三塔层）全绿后才推送；未经明确要求不得编写代码。**这条是流程铁律，适用于所有模块与轮次。**

## 三、通用 CLI 骨架（照抄即用）

```python
#!/usr/bin/env python
# -*- coding: utf-8 -*-
import argparse, json, os, sys
from pathlib import Path

sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
import bidcraft_core as core

try:
    sys.stdout.reconfigure(encoding="utf-8")
    sys.stderr.reconfigure(encoding="utf-8")
except Exception:
    pass

def dump(obj, args, human=""):
    print(json.dumps(obj, ensure_ascii=False, indent=2) if args.json else (human or obj))

def build_parser():
    p = argparse.ArgumentParser(prog="bidcraft", formatter_class=argparse.RawDescriptionHelpFormatter)
    p.add_argument("--root")
    p.add_argument("--enterprise")
    p.add_argument("--json", action="store_true")
    sub = p.add_subparsers(dest="cmd", required=True)
    ...
    return p

def main(argv=None):
    args = build_parser().parse_args(argv)
    try:
        args.func(args)
    except (core.LibraryError,) as e:
        print("❌ %s" % e, file=sys.stderr); sys.exit(1)

if __name__ == "__main__":
    main()
```

## 三之二、scripts/ 分包结构约定（v0.4+，防单文件过大 / 目录扁平化）

**目标结构**：脚本按「模块分包 + 共享层」组织，统一入口保持薄壳。

```
scripts/
├── bidcraft.py            # 统一入口（薄壳）：只做 argparse 组装 + 调度
├── _shared/               # 跨模块共享层
│   ├── core/              # 存储层包：basic/batch/inbox/ledger/lib/ops/retrieval/trash
│   ├── naming.py          # 命名规范引擎
│   ├── com_util.py        # 公共：控制台/表格输出
│   └── docx_util.py       # 公共：docx 读写
└── m<n>_<name>/           # 每个模块一个子包
    └── __init__.py        # 暴露 register_parser(subparsers) + 本模块各 cmd_*
```

**机制**：
1. **每模块一个子包** `m<n>_<name>/`：包内实现该模块的 CLI 子命令（`cmd_*`）、逻辑、存储，并在 `__init__.py` 暴露 `register_parser(subparsers)`，把本模块各子命令 `add_parser` 挂到传入的 `subparsers`。
2. **统一入口薄壳** `bidcraft.py`：只建主 parser、定义全局参数（`--root/--enterprise/--json`）、按顺序调用各模块 `register_parser(sub)` 挂载子命令、分发 `args.func(args)`；**不写任何业务逻辑**。
3. **共享层 `_shared/`**：跨模块公共能力放这里；存储能力集中在 `core/` 包（basic 基础 / batch 批量 / inbox 收件箱 / ledger 台账 / lib 企业解析 / ops 操作 / retrieval 检索 / trash 回收站）。
4. **单文件红线 ~500 行**：任何脚本接近即拆（如 `core.py` 拆为 `core/` 包；`util.py` 拆为 `com_util.py`/`docx_util.py`）。
5. **新增模块零侵入**：只加一个子包 + 在入口注册一行，不动既有代码。

**当前迁移状态**：✅ 全部模块已按分包落位（`scripts/bidcraft.py` 薄壳 + `scripts/m1_assets/`、`scripts/m2_template/`、`scripts/m4_tender/`、`scripts/m5_project/`、`scripts/m7_check/`、`scripts/m_feedback/` 子包 + `scripts/_shared/` 共享层）。

**分层仍沿用「三、通用 CLI 骨架」的三层**（逻辑层无 I/O / 存储层 / CLI 层），只是落位到分包结构。

## 三之三、测试金字塔与 CI/CD（开发必读）

**测试金字塔**（层越低用例越多越快，全部基于标准库 `unittest`）：
- L1 单元（`tests/unit`）：命名引擎等纯逻辑，最多最快。
- L2 集成（`tests/integration`）：存储层 core 等，真实数据依赖用例自动跳过（`BIDCRAFT_TEST_ENT`/`BIDCRAFT_TEST_PROJ` 环境变量注入，默认示例名）。
- L3 端到端（`tests/e2e`）：CLI 全流程，最少最慢。

**真实数据用例前置依赖清单化（⑬，必须遵守）**：凡真实数据依赖用例，skip 条件 = 用例实际依赖的数据文件清单，而非仅"企业根目录存在"。统一用 `tests/_data_guard.py`：
```python
from _data_guard import require_data, skip_unless_data
ok, missing = require_data(["项目级/<项目>/招标解析/素材清单.json"])   # 显式检查
@skip_unless_data(["项目级/<项目>/招标解析/素材清单.json", "项目级/<项目>/项目模板"])  # 类/方法装饰器
class TestReal(unittest.TestCase): ...
```
任一依赖缺失 → SkipTest（reason 自动列出缺失清单）；新写真实数据用例必须列出全部依赖数据文件。

**写后回读（⑭，必须遵守）**：凡对磁盘/台账/回收站有**写操作**的命令或核心函数，落盘后必须回读验证，失败即报错（fail fast），绝不假装成功。统一使用 `scripts/_shared/core/readback.py`：
- `verify_file(path)` 存在+非空；`verify_sha256(path, expected)` 哈希比对（移动不改变内容，最强校验）；`verify_json(path, fields)` 可解析+关键字段；`verify_docx_nonempty(path)` docx 段落数；`verify_consistency(ent)` 复用三方对账。
- 已接入：M1 apply（归档目标 sha256 与收件箱登记一致 + 台账存在 + 三方对账）、move_to_trash（目标存在/源移除/清单登记）；M2 tpl-import（模板文件+台账）；M4 tender（产物 json 可解析+关键字段、md/html 非空）；M5 proj-gen/fill（docx 非空+生成记录）。
- 只读验证、不自动修复：回读失败即报错由用户处置，不留半成品状态；新增写操作必须同步接入回读并补对应单测。

**规则**：新增逻辑先补对应层测试再实现；提交前本机三塔层全绿（`python -m unittest discover -s tests/<层> -t .`，需 `pip install python-docx Pillow`）；真实数据本地回归用 `tests\run_local_regression.bat`。

**CI**（`.github/workflows/ci.yml`）：push/PR 触发（Python 3.12 Windows + 双平台 py_compile），并跑 CodeQL 代码扫描；main 分支失败自动开 Issue。
**CD**（`.github/workflows/release.yml`）：打 `v*` 标签时打包发布 skill 可分发包（排除素材库/缓存）。
**部署**：merge main 自动触发 self-hosted runner → 生产 `E:\标书匠生产` 拉取+冒烟+记录；另有定时兜底（每 6 小时）与使用入口自动拉取。
