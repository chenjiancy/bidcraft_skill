# M4 招标文件解析 · 操作手册

> 适用：bidcraft skill（标书匠）· 模块 M4 招标文件解析
> 形态：**skill 驱动 agent**——解析能力由 agent 完成，脚本只做编排与存取
> 对应需求：`references/M4-招标文件解析-需求对齐.md`（**v2.1 定稿：9 模块解析框架 + 双通道解析 + 响应文件格式独立文件 + 双确认闸门**）
> 版本：v2.1（2026-10-07）

---

## 一、这套东西怎么分工

| 角色 | 负责什么 | 载体 |
|------|----------|------|
| **agent（语义解析）** | 读取招标文件、按 9 模块解析（**通道B**）、生成投标要点 + 素材清单、逐条带原文锚点、对照素材库给出匹配建议、裁决双通道差异 | 豆包 / WorkBuddy / hermes / trae work 等 |
| **脚本（确定性）** | 项目级目录存取、原文落盘、**通道A 文档解析（规则引擎抽取确定性字段）**、**响应文件格式章节脚本化提取**、双份产物（文本+JSON）落盘、**双通道差异比对**、素材库 `query()` 对照、缺料对照表 | `scripts/bidcraft.py` + `scripts/m4_tender/` |
| **用户（决策）** | **确认解析结果**（含裁决双通道差异）、提供素材清单（可选）、确认对照结果、确认最终素材清单与投标要点 | 对话 |

- **平台无关**：解析工作流只依赖 agent 通用能力（读文档/图片、语义理解、写文件），不依赖任何平台私有能力；图片 OCR 由各平台 agent 自带能力完成。
- 依赖：**Python 3.8+ 标准库**（脚本侧），无第三方包；PDF 结构化提取可选 PyMuPDF（`pip install pymupdf`），未安装时自动降级要求 `--text-file`（既有路径不变）。`.doc`（老格式）脚本不支持，用 Word COM 转文本（GBK→UTF-8）后以 `--text-file` 传入。

## 二、标准流程（agent 编排，一次一个任务，两个确认闸门）

> 对应需求 v2.0：招标解析 → **用户确认解析** → 素材清单（询问两分支）→ **用户确认素材清单** → 商务标制作

### 阶段 ①｜定位项目与确认目录

1. 确认企业（`--enterprise`，单企业可省略）。
2. **项目名由 agent 解析招标文件后自动确定**（从招标文件提取项目名称，如「XX安置房项目监理」），不再由用户先给。
3. 脚本用该项目名自动创建/复用项目级目录结构（幂等）：`<软件根>/<企业>/项目级/<项目名>/招标解析/`（含 `源文件/` 子目录）+ **`项目资料/`**（项目独享资料，与招标解析同级）。
   - **对话要点**：项目名自动确定后向用户复述确认；若招标文件未载明项目名，则询问用户。

### 阶段 ②｜读取招标文件（归档原件 + 提取正文）

- 用户上传的招标文件（PDF / DOCX / 图片等）→ `tender-extract --file <原件>` **自动归档**到 `招标解析/源文件/源文件_<项目名>.<ext>`（幂等：同内容重复上传跳过；不同内容报错不覆盖）。
- **DOCX / TXT / MD**：脚本内置提取正文 → `原文_<源名>.txt`。
- **PDF**：脚本内置结构化提取（PyMuPDF 表格/多栏感知）→ `原文_<源名>.txt`。
- **图片 / 纯扫描件 PDF / .doc**：原件同样归档；正文由 agent 提取（OCR / Word COM 转文本 / 平台文档解析）后以 `--text-file` 传入 → `原文_<源名>.txt`。
- **对话要点**：原文提取后先核对——页数/字数合理、无乱码缺页，再进入解析。

### 阶段 ③｜双通道解析（核心，语义工作）

**通道A 文档解析（脚本规则引擎，确定性）**：`tender-rule` 从原文抽取**关键事实字段**（项目编号/金额/日期/截止时间/服务期/有效期/保证金/联合体/电子纸质/实名制/资质/人员数量/百分比等，规则表 `m4_tender/rule_extract.py` 可增行，11 条规则），每条命中带原文行号锚点 → `文档解析_<项目名>.json`。适用确定性要素（格式固定、表述规范的字段）；拿不准的字段不写规则（避免误报污染差异）。

**通道B agent 语义解析（9 模块）**：agent 按**解析内容框架 v5（9 模块）**通读原文并逐条摘录，**每条要点必须带原文锚点**（条款号 / 页码 / 原文摘录），防废标核查时可回看原文：

| # | 模块 | 解析内容 | 注意 |
|---|------|----------|------|
| 1 | 项目基本信息 | 名称/编号/采购人/代理/预算限价/资金来源/服务期/**投标截止日期**/**电子标或纸质标**/**实名制或非实名制**/开标/有效期/保证金 | 电子/纸质、实名/非实名不影响标书制作，但帮助制作人员了解投标要求 |
| 2 | 资格条件 | 资质等级、总监要求、联合体 | **不解析**登记方式/登记要求 |
| 3 | 人员配备 | 岗位/人数/证书/注册单位/兼职限制/社保/**委托代理人要求（有无社保）** | |
| 4 | 项目概况与监理工作内容 | 改造范围、栋数户数、监理工作内容/范围 | **技术标写作依据，必须解析** |
| 5 | 评分办法 | 分值/计分规则/认定口径 | |
| 6 | 报价要求 | 上限（废标线）、报价形式、费率折算 | **报价金额由用户提供** |
| 7 | 响应文件编制与递交 | 份数/装订/密封/递交/文件组成（摘要） | 格式全文见独立文件 |
| 8 | 废标/否决红线 | 不予接收、初审不通过项、流标 | **不解析**信用黑名单 |
| 9 | 待确认/缺失项 | 招标文件未写但影响投标的内容 | 有缺口才列 |

**双通道差异比对（v2.1，脚本已落地）**：`tender-diff` 读 `文档解析_<项目名>.json`（通道A）与 `投标要点_<项目名>.json`（通道B）做字段级比对 → `双通道差异_<项目名>.json/.md`。差异类型三类：①事实值不同（编号/金额/日期/人数/百分比等取值不同，含数字归一化——48.86 vs 48.86万元视为一致）；②存在性差异（通道A 有关键字段、通道B 未解析到）；③语义冲突（对同一要求解读矛盾，由 agent 在投标要点 diffs 中标注）。表述详略差异不列示。**agent 把差异并入投标要点「双通道解析差异」块，随闸门①由用户裁决**。

**不解析（除非用户明确要求）**：**合同内容**——合同协议书、通用/专用合同条件、附件（考核办法、违约金、驻场要求、履约承诺、安全目标等）、监理管理考核打分表；商务标、技术标均不引用。

**响应文件格式独立文件**：招标文件「响应文件格式（投标文件格式）」章节**全文提取**为 `响应文件格式_<项目名>.txt`——**一模一样、一个字都不能更改**（除非人工修改）；`tender-fmt` 自动定位章节（取最后一个标题匹配跳过目录条目、尾部清理空行/页码）切片提取，`--start/--end` 可覆盖；提取后与原文逐行比对校验（切片一致）。它是**内容地基**（格式排版由企业模板控制），供 M2 项目模板生成时做内容校验。

> **诚实原则**：拿不准的条款标注「待确认」，不臆断；废标红线宁可多列不可漏；解析不了或招标文件未写的内容列入模块 9。

### 阶段 ④｜生成投标要点（产物 A）→ **用户确认（闸门①）**

- 按 9 模块组织为 Markdown 文本，同时生成同内容 JSON（机读，供 M5/M7 调用）。
- 展示格式：**核对速览（30 秒结论）+ 逐模块明细（每条带原文出处）+ 双通道解析差异块 + 红线块独立 + 待确认块**——便于用户快速核对完整性、正确性。
- **对话要点（闸门①）**：投标要点（含双通道差异块）生成后**必须先展示给用户核对**，用户确认解析完整、正确并裁决差异后，才进入素材清单环节；**未确认不得静默推进**。

### 阶段 ⑤｜生成素材清单（产物 B）—— 先问特定清单（两分支）

1. **询问用户：「是否有素材清单上传？」**（可以有，也可以没有）
   - **情况 1（用户上传了素材清单）**：结合用户清单查询素材库——**用户指定的素材直接查询素材库核对**（有/没有/缺部分）；**用户未指定但项目需要的素材**，查询素材库后**推荐给用户**。
   - **情况 2（用户未上传素材清单）**：直接查询素材库，**匹配最适合的素材推荐给用户**。
2. agent 从资格要求与评分标准中推导素材项：**大类/子类（对齐 M1 素材库）+ 用途（对应资格项或评分项）+ 必须/加分 + 来源条款**。
3. 产出：素材清单（文本+JSON）+ **已有/缺失对照表**（缺硬性素材标红 = 废标风险提示）+ 匹配建议。
4. **对话要点（闸门②）**：素材清单产出后**待用户确认**；缺料标红项确认是否补充；匹配建议确认是否采纳。确认后进入下一步。

### 阶段 ⑥｜进入下一步（M2 项目模板 / M5 商务标，后续模块）

素材清单经用户确认后，作为后续模块的取用依据（项目模板内容校验、商务标按清单逐项取素材填充）。

## 三、产物 A 模板：投标要点（9 模块 v5）

```markdown
# 投标要点 · <项目名>（<招标文件>）

## 0. 核对速览
- 项目编号 ｜ 预算/限价 ｜ 投标截止/开标 ｜ 电子/纸质标 ｜ 实名/非实名
- 评标结构（各模块分值）｜ 人员红线 ｜ 报价红线 ｜ 🔴待补项
（30 秒看完结论）

## 一、项目基本信息
- 项目名称：...（原文锚点）
- 投标截止日期：...（原文锚点）
- 电子标/纸质标：...｜实名制/非实名制：...
- ...（逐条带原文锚点）

## 二、资格条件
- 资质等级 / 总监要求 / 联合体（逐条带原文锚点）

## 三、人员配备
- 岗位/人数/证书/注册单位/兼职限制/社保
- 委托代理人要求（特别是有无社保要求）

## 四、项目概况与监理工作内容
- 改造范围 / 栋数户数 / 监理工作内容（技术标写作依据）

## 五、评分办法
- 评标方法 + 每个评分项（分值/得分条件/认定口径/需提交证明材料）

## 六、报价要求
- 报价上限（废标线）/ 报价形式 / 费率折算规则
- 报价金额：由用户提供（不解析）

## 七、响应文件编制与递交
- 份数/装订/密封/递交时间地点方式/文件组成（摘要）
- 格式全文见《响应文件格式_<项目名>.txt》（一字不改）

## 八、废标/否决红线（独立成块）
- 不予接收情形 / 初审不通过项 / 流标条件（逐条带原文锚点）

## 九、待确认/缺失项
- （招标文件未写但影响投标的内容；有缺口才列）

## 双通道解析差异（N 条，v2.1）
| # | 解析项 | 通道A文档解析值（出处） | 通道B语义解析值（出处） | 差异类型 | 待裁决 |
|---|---|---|---|---|---|
| 1 | 项目编号 | HXTD-2026-018（公告二） | HXTD-2026-018（公告二） | 一致（不列示） | - |
| 2 | 履约保证金 | 前附表：不采用 | 投标函4：承诺递交履约担保 | 语义冲突 | 用户裁决 |
```

> 机读 JSON 为同内容的 `{"modules": [...], "diffs": [...]}` 结构（与文本一一对应）。

## 四、产物 B 模板：素材清单

```markdown
# 素材清单 · <项目名>

> 用途：从素材库提取 + 提示补充 + 商务标制作基础
> 解析结果已确认：是/否 ｜ 用户提供特定清单？是/否（如是，优先按其核对）

| 大类（对齐M1） | 子类 | 用途（对应资格项/评分项） | 必须/加分 | 来源条款 | 对照结果 | 匹配建议 |
|---|---|---|---|---|---|---|
| 资质 | 企业资质证书 | 资质等级要求（甲级） | 必须 | 3.1 | ✅已有 | - |
| 人员 | 总监理工程师/注册证书 | 总监资格（评分项） | 必须 | 3.2 | ⚠️缺部分 | 建议：陈XX |
| 业绩 | 监理合同/验收报告 | 类似业绩（评分项） | 加分 | 评标办法 | ❌缺失 | 需补充 |
| 财务 | 中小企业声明函 | 价格扣除 | 加分 | 前附表 | ❌缺失 | 需补充 |
| ... | ... | ... | ... | ... | ... | ... |

## 缺料提醒（废标风险）
- ❌ 必缺项：...（不补 = 废标风险 / go-no-go 提示）
- ⚠️ 加分项缺失：...
```

> 机读 JSON 为同内容 `{"items": [...]}` 结构；对照结果字段：`✅已有 / ⚠️缺部分 / ❌缺失`（脚本三态：`✅已有 / 🔴缺失·必须 / ⚠️缺失·加分`）。

## 五、对话检查点（不得静默跳过）

1. 建项目目录前：确认**项目名**。
2. 原文提取后：核对**字数/页数、无乱码缺页**。
3. **双通道解析**：`tender-rule`（通道A 文档解析）产出确定性字段（带原文行号）；agent（通道B）产出 9 模块要点；`tender-diff` 比对两通道**实质差异**（事实值不同/存在性差异/语义冲突）→ 差异块。
4. **投标要点生成后（闸门①）**：展示给用户核对 9 模块完整性/正确性 + 裁决差异——**用户确认后才进入素材清单环节**。
5. 响应文件格式独立文件（`tender-fmt`）提取后：与原文**逐行比对校验**（一字不改）。
6. 生成素材清单前（闸门②前置）：询问**是否有素材清单上传**（有 → 结合用户清单查素材库，用户指定直接查、未指定项目需要则查库推荐；没有 → 直接查库推荐）。
7. 对照结果：**缺料标红项**确认是否补充；**匹配建议**确认是否采纳；**素材清单经用户确认后**才进入下一步。
8. **流程铁律**：需求先复述对齐 → 用户确认 → 联网查建议 → 执行（模块开发规范 §二.9）。

## 六、命令速查（脚本，v0.8.x 已实现）

```bash
python scripts/bidcraft.py [--root <软件根>] [--enterprise <企业>] [--json] <子命令> [参数]
```

| 命令 | 作用 |
|------|------|
| `tender-init --project <项目名>` | 创建/复用项目级目录结构（幂等，项目名禁路径分隔符；项目名由 agent 解析后自动确定）：**`招标解析/`（M4 产物）+ `项目资料/`（项目独享资料）** |
| `tender-extract --project <名> --file <原件> [--text-file <已提取文本>]` | **归档原件**（任意格式 → `源文件/源文件_<项目名>.<ext>`）+ 提取原文：DOCX/TXT/MD/PDF 内置（PDF=PyMuPDF 表格/多栏感知，未装时降级）；图片/纯扫描件/.doc 配 `--text-file`（agent 提取文本） |
| `tender-fmt --project <名> [--start <行> --end <行>]` | **v2.1 响应文件格式脚本化提取**：自动定位「响应文件格式/投标文件格式」章节（取最后一个标题匹配，跳过目录条目；尾部清理空行/页码）→ `响应文件格式_<名>.txt`（一字不改；--start/--end 1 基行号可覆盖） |
| `tender-rule --project <名>` | **v2.1 通道A 文档解析**：规则引擎抽取确定性字段（带原文行号锚点）→ `文档解析_<名>.json` |
| `tender-diff --project <名>` | **v2.1 双通道差异比对**：通道A vs 通道B（投标要点）→ `双通道差异_<名>.json/.md`（差异并入投标要点 diffs 块，用户裁决） |
| `tender-parse --project <名> --points-md <md> --points-json <json> --list-md <md> --list-json <json>` | 校验并落盘双份产物（投标要点 / 素材清单，文本+JSON；JSON 须按模板含 modules/items，**v2.1 起投标要点强制 9 模块全覆盖 + diffs 结构校验**，带 BOM 亦可） |
| `tender-check --project <名>` | 素材清单逐项对照素材库 → `素材对照_<名>.csv` + 缺料标红（🔴必缺/⚠️加分缺） |
| `tender-show --project <名> [--what points\|list\|check]` | 人读查看（默认投标要点） |

- 产物落位：`<软件根>/<企业>/项目级/<项目名>/招标解析/`（`源文件/`、原文、**响应文件格式_<项目名>.txt**、**文档解析_<项目名>.json**、**双通道差异_<项目名>.json/.md**、投标要点、素材清单、素材对照）；项目独享资料放同级 `项目资料/`。
- 素材对照状态三态：`✅已有 / 🔴缺失·必须（废标风险）/ ⚠️缺失·加分`。
- 退出码：`0` 成功 / `1` 参数或状态错误（无部分失败场景）。
