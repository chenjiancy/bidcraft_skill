### M1 规则增强：归档关键字同名判定（用户确认制）
- **背景**：原有 `on_conflict` 仅在 `apply` 时按「目标文件路径已存在」判定，默认 `keep_both` 自动加 `_2` 后缀，**不主动让用户确认**。用户新增规则：收件箱归档重命名时，**关键字相同即判定为同名素材，交由用户确认如何处理**。
- **实现**（bidcraft_core.py）：
  - `propose`：构建「同类别 → 关键字集合」台账索引，对每项按**同大类 + 同子类 + 关键字有交集**判定同名 → 置 `is_name_conflict=true`、`on_conflict=""`（未确认）、`conflict_with`（冲突对象 rel_path 列表）、`conflict_in_batch`（批次内同名标记）。
  - `apply`：`is_name_conflict` 且 `on_conflict` 为空 → **拒绝归档**，提示先确认处理方式（keep_both / skip / trash_old），退出码 2。
  - 顶部新增 `from collections import defaultdict`。
- **文档**：M1-素材库-操作手册.md 提案字段表补 `is_name_conflict/conflict_with/conflict_in_batch`，`on_conflict` 说明改为"同名时必须用户确认"；对话检查点第 5 条明确判定标准与"确认前不得 apply"。
- **验证**（冒烟全绿，临时脚本已删）：①首归档无冲突；②同关键字→标同名、列冲突对象、`on_conflict` 为空；③未确认 `apply` 被拒(exit 2)且提示正确；④确认 `keep_both` 后归档成功；⑤不同关键字不误判；⑥`py_compile` 三脚本通过。
- **耗时**：约 30 分钟。

### ⑨ docxtpl 小规模对比评估（P2 · 12 条建议最后一项）
**背景**：建议 P2-9「评估用 docxtpl（Jinja2 语法）替代部分自研 XML 操作（行循环/合并单元格更成熟）」。本项是评估性质：不改产品代码，产出对比证据 + 结论，是否引入由用户拍板。前提约束：产品需求「文字 100% 来自招标原文、保留原文样式、模板零人工改造」。
**实验环境**：dev/docxtpl_eval/（不入库 _deps/）：docxtpl 0.20.2 + jinja2 3.1.6 局部 pip install --target（不污染全局）；python-docx 生成对照模板。
**实验设计**（build 对照模板 tpl_self / tpl_docxtpl，同一原文范本）：
- 特征覆盖：标题黑体16+bold、正文宋体12、跨 run 拆分的【项目名称】占位、3 列表格（表头+范本行【姓名】【出生年月】【备注】+尾部（盖章））、tblBorders 全框；
- 路线 A 自研（render_self.py 53 行）：docx_util.set_para_text 跨 run 替换 + 范本行 deepcopy 复制 3 次逐格替换——即现有产品公共工具路径；
- 路线 B docxtpl（render_docxtpl.py 29 行）：DocxTemplate.render(DATA)，模板注入 {{ project_name }} 与 {%tr for/endfor %} 行循环；
- 测量：固定文字 6 项保真、run 样式（字体/字号/bold）、表格边框、表头 bold、循环行 trPr、行数、依赖。
**结果（对比结果.json）**：
- 文字保真：两路线 6/6 全 true，平局；
- 样式保留：标题黑体16/bold、正文宋体12、tblBorders、表头 bold 两路线完全一致；循环行 trPr 均为空（模板行本无 trPr）；
- 行循环展开：self=4 行、docxtpl=4 行（表头+3 数据），首次实现在大模板不展开（1 行），修复后等价；
- 代码量：自研 53 行 vs docxtpl 29 行（约减半）；
- 依赖：自研 = python-docx + docx_util（现有）；docxtpl = 新增第三方 docxtpl + jinja2（CI 依赖矩阵需扩展）。
**踩坑（docxtpl 0.20.2 行循环语义，源码 patch_xml 实证）**：
1. {%tr for %} 标签必须独占一行（所在 <w:tr> 整行被正则剥掉、仅提取标签），循环体是**标签行与 {%tr endfor %} 行之间的行**——官方示例正是 标签行/变量行/结束标签行 三行结构，并非「循环行本身重复」。第一版把 for/endfor 塞进范本行同格段落 → 大模板只输出表头 1 行；修正后正常展开 4 行。
2. {%tr endfor %} 所在行必须有 <w:t> 节点才能被剥除——add_row() 生成空行无 w:t，标签写入失效报「looking for endfor」；用 deepcopy 范本行保结构解决。
3. 标签必须落在单元格第一段（0.20.2 正则按 <w:tr> 整体匹配剥行，段落位置敏感）。
4. 跨 run 变量段仍需手工处理（清 runs[1]、写 runs[2]），docxtpl 不豁免「跨 run 拆分」问题本身。
**结论（定稿）**：**不整体迁移 docxtpl**。
- 功能等价但模型不匹配：docxtpl 把「模板作者手工注入 Jinja 标签」前置为必要条件（{{ }} 与 {%tr %} 三行结构），与产品「招标原文 100% 契约、模板零改造、保留原文样式」直接冲突——agent 仍需在生成阶段注入标签，工作量未消失而是转移；
- 行循环/标签位置/独立行等约定版本敏感（0.20.2 与直觉相反），复杂真实模板（合并单元格、嵌套表、图片占位 10 处、简历表份数复制）风险不可控，且会新增 CI 第三方依赖；
- 自研路线经 ① 的 docx_util 工具化后已解决最大痛点（跨 run 替换/样式保留），代码虽多但零依赖、可单测、行为确定。
**保留场景**：若未来支持「agent 作者自动生成带 Jinja 标签的新模板」（new-template-only 场景），docxtpl 可作为候选，但需先在真实复杂模板上专项验证合并单元格与嵌套表后再决定。
**验证**：对比脚本 run_compare.py 可独立重跑（产出 对比结果.json）；本项不新增仓内测试（评估实验在 dev 下，docxtpl 未进 CI/产品依赖）。
