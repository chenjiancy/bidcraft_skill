## 0. 需求复述（C1 需求对齐）

将豆包内置 word 技能中 **read.py（docx 结构深读器）** 与 **audit.py（docx 格式/结构审计器）** 的**能力逻辑**移植到 bidcraft 仓库共享层，保持**平台无关**（纯 python-docx + lxml + 标准库，不依赖豆包私有能力如 lark-cli WPS 通道），服务三个消费场景：

1. **M2 企业模板制作**：从已完标书「源文即成品模板」制作企业级模板库母版时，深读器提供分节/表格合并/图片锚点/页眉页脚/样式继承的结构证据；审计器提供「企业模板页数 = 源文件页数」（D21）与格式一致性校验；
2. **M5 生成校验**：文字逐字/页数/格式一致性的代码硬校验基座；
3. **M7 检查与「企业模板库/项目模板/商务标三者格式完全一致」硬校验**：格式结构/页数/占位符维度的机器检查能力基座。

产出：`scripts/_shared/docx_tools/`（docx_reader + docx_audit + CLI `docx-read`/`docx-audit`）+ 单测 + 文档回填。**本清单确认前不写任何代码。**

## 三、偏离项（C 级，用户拍板后执行）

1. **能力子集（非全量移植）**：read.py（105KB）与 audit.py（216KB）仅移植标书场景需要的核心集，不做全量；移植方式为**能力逻辑借鉴重写**（接口契约与解析规则对齐、代码按 bidcraft 风格重写），非整文件复制，仓库内不引用豆包技能路径；原文件版权与来源不随代码分发。
2. **CLI 挂载位置**：共享工具以 `_shared/docx_tools` 子包挂 `docx-read`/`docx-audit`，不使用 m* 业务模块命名（非新业务模块，不占 M11 序号）。
3. **不做业务重构**：本次仅新增共享基座，m7_check 不重构、M5/M2 不接线（接线与硬校验改造留待后续立项）。

## 四、验证计划

1. **L1 单测**：docx_reader 各维度最小 fixture 断言（正文/分节/表格合并/媒体/页眉页脚/样式继承）；docx_audit 的 issue 契约、结构 hash、基线差异过滤断言。
2. **Golden 交叉验证**：真实已完标书 docx（如 `资格证明及辅助资料表.docx` 65 页版与 `（修）2026年度县委党校...docx`）跑 `docx-read` 各维度 + `docx-audit`，与 word skill `read.py` 输出逐项交叉比对一致性，验证移植正确性。
3. **回归**：unit + integration + e2e 三塔层全绿（`python -m unittest discover -s tests/<层> -t .`），提交前向用户披露。
4. **性能冒烟**：65 页资格表 docx 读取/审计耗时记录，写入开发日志。
