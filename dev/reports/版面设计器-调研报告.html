能力形态说明对版面设计器的意义

02

行业调研：五条技术路线

公开资料归纳（详见文末来源），定性评估基于资料判断
A

全真 WYSIWYG 分页编辑器

ONLYOFFICE Docs · 10Play DocEx

以 DOCX 原生文档模型直接渲染（Canvas 逐像素绘制，无 HTML 代理层）；浏览器与 Word 换行/分页引擎不一致，需要自建分页引擎（spacer 注入 + 逐节点测量 + px↔缇转换 + 逐字测换行）。

投入极高 所见即所得
B

模板即版面（占位符填充）

docxtemplater · Carbone · apex-docx-pdf

「DOCX 本身就是版面工件」：版面在 Word 里排好，数据用标签注入（{{x}} / 循环 / 条件 / 图片模块），渲染器把受限数据确定性套进已排好的结构。任何会 Word 的人都能改模板。

与商务标母版范式完全同源
C

低代码可视化设计器

LowCodeEngine · 表单设计器（填鸭等）

三层四端范式：组件树 JSON Schema 为唯一数据源；「组件/物料库 | 拖拽画布 | 属性面板」三区联动；协议-引擎-生态-平台分层。前端 Vue/React + 拖拽库（vuedraggable 等）即可实现。

UI 架构业界标准范式
D

直写 OOXML 确定性渲染

dom-docx · kritidocx · python-docx（本项目现状）

HTML/CSS 与 OOXML 是两套排版模型（流式 vs 固定页面、属性 350+ vs 200+），经 Word「HTML 导入模式」必然有损。工程化解法 = 跳过 HTML 代理，直接生成符合 OOXML 规范的 docx。

导出引擎现状即此路线
E

领域标书工具

品茗智绘 · 新点标桥 · WPS 365 智能文档 · Word/WPS 排版插件

共性范式：内置版式预设（投标专用）+ 一键自动排版（目录/层级编号/字体/页面规则）+ 合规/暗标检查（200+ 项）。多为 Word/WPS 插件或云端工作台形态，非自建编辑器。

印证「预设 + 引擎 + 检查」领域范式

03

关键洞察（调研证据）

每条均有公开资料支撑
① 商务标母版范式 = 业界主流（模板即版面）

apex-docx-pdf 明确：「DOCX 是版面工件，Word 让模板作者直接控制页面几何、段落样式、编号、固定表格网格……渲染器把受限数据确定性套进已排好的结构」。docxtemplater / Carbone 同为「Word 排版 + 标签填充」，与本项目 M2/M5 v2.0 布局样板范式同源。

github.com/craig-bredenkamp/apex-docx-pdf · docxtemplater.com · carbone.io
② 全真 WYSIWYG 的代价：浏览器与 Word 渲染不一致

DocEx 实践：浏览器和 Word 的字体渲染、换行算法、页边距处理完全不同，「1px 行高差异累积到第 10 页会差一整段」。为此需自建分页引擎（spacer 注入、逐节点测量、px↔缇换算、逐字测换行）。ONLYOFFICE 则以 Canvas 自绘 + 统一文档模型规避。两者投入都属产品级。

10play.dev/blog/docex · onlyoffice.com/blog
③ HTML→OOXML 天然有损，工程化解法是直写 OOXML

HTML+CSS（流式、约 350+ 属性）与 OOXML（固定页面、磅/缇、约 200+ 属性）是两套排版模型；Word 的 HTML 导入模式对中文字体、行距、复杂嵌套映射不完整。行业结论：导出前完成解析转换、直接生成符合规范的 .docx（本项目的 python-docx 路线即此）。

developer.volcengine.com（AI 导出链根因分析）
④ 设计器 UI 的标准范式：组件树 Schema + 三区联动

低代码引擎共识：组件树 JSON Schema 是唯一真源，「物料/组件库 | 拖拽画布 | 属性面板」三端同步（LowCodeEngine 分层架构、填鸭表单 Vue3 + vuedraggable 实现）。这正是把 V3 原型「表单式风格配置屏」升级为可视化设计器的现成模式。

lowcode-engine.cn · tduckcloud.com · cnblogs.com
⑤ 领域产品印证：预设 + 自动排版 + 合规检查

品茗智绘（一键生成技术标/施组、可设置标书格式、自动排版、自动目录）、新点标桥（按招标要求自动设置暗标格式）、WPS 365 智能文档（投标专用版式预设、AI 排版引擎、200+ 合规检查）。没有一家为标书自建分页编辑器——都在「预设引擎 + 确定性排版 + 规则检查」上发力。

pinming.cn · bqpoint.com · 365.wps.cn
⑥ 本项目独特约束：暗标硬规则与页面独占规则

与通用文档设计器不同，本设计器必须把「暗标强制项（font=dark-safe、图片二选一、页眉页脚二选一、微观六组自动注入）」「仿宋/28 磅行距/页面独占」「两图一页/居中/间距」作为设计时约束内嵌——保存即校验，而不是事后检查。

推荐方案：三层「版面预设设计器」

数据层 + 引擎层 + 设计器层，最大化复用既有体系

架构要点：① 设计器只产出/修改 Schema，不改渲染引擎、不改正文 md——延续「内容与版式解耦」；② 预览用真实 docx 渲染回显（M0 已具备 Word COM 冒烟能力，可直接复用）；③ 商务标母版工作台（占位符索引/样板行管理）可作为二期并联模块，数据走「母版 docx + 键名规范表」；④ 暗标规则、页面独占等业务规则进 Schema 的「页面规则清单」，设计时即校验。

与既有体系的关系（不推倒、只叠加）

既有资产版面设计器中的角色
layout-presets.json v1.4升级为 Schema v2：保留 15 组可增行表，新增「区域组件树」与「页面规则清单」两组；v1 数据向后兼容

M2/M5 商务标母版（docx）二期：母版制作工作台（占位符索引可视化、样板行/页管理、缺图披露预览），沿用路线 B 范式
05

落地路径与待拍板决策点

决策权限表：未列入权限表一律 C 级（用户拍板），以下为我的倾向
Q1

设计器定位：先覆盖哪条链路？

A. 技术标排版预设设计器（画布 + 属性面板编辑 15 组预设 + 样张预览）——与 M6 现有资产最顺，一期闭环最快

B. 商务标母版工作台（Word 内辅助：占位符索引/样板行管理）——沿用模板即版面范式，偏向 Word 插件/伴生工具

C. 两者统一的「版面设计中心」——一次规划、分期建设（先 A 后 B）

我的倾向：C 统一规划，一期先做 A —— 技术标预设已有数据模型与渲染引擎，可最短时间形成「编辑 → 预览」闭环；商务标母版需先解决 Word 侧交互，放二期。
Q2

画布预览通道（docx → 图片回显）

A. 本机 Word COM 渲染（M0 env-check 已含 Word COM 冒烟，Windows 桌面端最保真）

B. LibreOffice headless 转 PNG（跨平台、无 Office 授权依赖，渲染与 Word 略有差异）

C. 网页端 CSS 模拟排版（快、无需本地依赖，但与最终 docx 存在必然偏差，仅作示意）

我的倾向：A 为主、C 兜底 —— 标书交付以 Word 打开为准，预览必须贴近 Word；C 可用于快速交互态。LibreOffice 作为可选项后补。
Q3

设计器形态与承载

A. 独立单页 HTML 工作台（延续 V3 原型技术路线，本机打开即用，后端走 CLI/脚本）

B. 内嵌进标书匠软件（与向导、编辑器同屏，数据走软件本地目录）

C. A 先做原型验证 → 定稿后再并入软件

我的倾向：C —— 先在 dev/prototypes 出可交互原型（对齐「UI 不是自造逻辑」原则），三区架构验证后并入正式 UI。
Q4

一期范围（最小闭环）

A. 预设编辑 + 暗标/页面规则校验 + 样张一键出图（不引入拖拽）——4 周级

B. A + 页面区域组件拖拽（封面/页眉页脚/章节页可视化搭）——8 周级

C. 全功能（含商务标母版工作台）——12 周级

我的倾向：A —— 项目铁律「每一步人工确认、确定性脚本执行」；一期先把「编辑-校验-预览-落盘」做扎实，拖拽类交互二期再上。

下一步（待您拍板后执行）

① 确认 Q1–Q4 → ② 落盘《版面设计器-需求对齐.md》→ ③ 出三区工作台 HTML 原型（复用 V3 风格语言 + layout-presets.json 真实数据）→ ④ 接 tech-layout 后端做「保存/校验/出样张」→ ⑤ 原型评审后并入正式 UI。按贵司「规则对齐闸门」流程，动手前会先输出规则对齐清单。
