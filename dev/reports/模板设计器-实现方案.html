2

需求定位：模板设计器要解决什么

定义（本报告口径）

模板设计器 = 把「文档模板」作为可设计对象：使用者从部件库（封面 / 扉页 / 目录 / 正文版式 / 页眉页脚 / 结尾）拼装结构、从预设库（版面 / 配色 / 字体 / 图表样式）引用样式、绑定占位符（企业名 / 项目名 / 章节流 / 图片位），最终产出一份模板描述 JSON，由渲染引擎生成正式 docx。

它与已有版面设计器的关系：版面设计器管「同一份正文内容换皮」；模板设计器管「整本文档的结构与样式编排」。两者共用同一份预设数据源，模板设计器是版面设计器的结构扩展 + 样式引用。

三条硬约束（沿用项目既有原则）

  • 无 UI 亦完整可用：所有能力落实在 skill（对话工作流）/ 文档（数据模型与规则）/ 代码（CLI + 引擎 + 校验）三层；UI 只作演示原型。
  • JSON 为权威源：模板描述、预设、部件清单都是文件，可入仓、可 diff、可校验，UI 只是它的渲染视图。
  • 人工确认闸门：设计落盘、应用到项目、导出 docx 均需 --confirm，与 tech-layout --apply-combo 一致。

行业方案调研（联网）

候选 A：GrapesJS Studio SDK（Document 模式 + Absolute Mode）

多用途 Web Builder 框架，2025 年新增文档工程（Document Projects）：预设 A4/A5/US Letter 等打印幅面、屏幕预览与打印一致、pageBreak 分页组件、Printable 插件；Absolute Mode 插件支持像素级自由定位（固定字段、签名、标签、卡片）。框架无关（vanilla JS 可嵌入），适合做「页面 / 邮件 / 文档」类拖拽编辑器。

  • 优势：文档版式所见即所得成熟度高；社区与文档完善；可嵌入现有 HTML 工作台思路。
  • 短板：产物是 HTML/CSS 描述，不直接是 docx，需二次映射到 python-docx XML（项目引擎可承接）；Studio SDK 商业版需授权，开源 GrapesJS 核心需自行组装。
来源：grapesjs.com/blog/release-document-builder · GrapesJS Studio SDK Printable · grapesjs.com/blog/grapes-release-absolute-mode

候选 B：AavanamKit（designer 组件 + headless engine）

开源文档生成套件：前端是 React 拖拽设计组件（@aavanamkit/designer），后端是 headless Node 引擎（@aavanamkit/engine），同一模板可导出 PDF / DOCX / HTML；带布局感知的表格分页与样式保真。

  • 优势：「设计器 ↔ 渲染引擎分离」的架构与本项目理念一致，多格式导出思路可直接借鉴。
  • 短板：技术栈是 React + Node.js，与项目 Python 引擎不同；docx 保真度依赖其实现，交付标的仍是「HTML 派生文档」，对标书式 docx 原生格式（仿宋/行距/域代码）需要重写映射。
来源：npm @aavanamkit/designer · npm @aavanamkit/engine · Product Hunt AavanamKit

候选 C：docxtpl / python-docx 系（占位符模板引擎）

docxtpl = python-docx + Jinja2：在 Word 里写 {{ 变量 }} / {% 循环 %} 占位符，渲染时填充；docxspec / pymsword 是同族结构化封装。

  • 优势：与项目 tech-export 同栈（python-docx）；docx 原生保真最高；离线零依赖。
  • 短板：不是可视化设计器——模板改动要改 Word 文件本身，无法做到「部件编排 + 实时预览」；占位符语法对非技术人员有门槛。
来源：python-docx-template 文档 · python-docx 文档 · docxspec · PyPI · pymsword · PyPI

候选 D：表单设计器启示（Everright-formEditor 等）

字段/区块级拖拽设计器（layui-form-design、vue-form-generator、Everright-formEditor、shadcn Form Builder 等），核心模式是「左组件库 + 中画布 + 右属性面板」三栏布局、拖拽落位、属性联动。

  • 价值：交互范式可直接迁移到版面/模板工作台（左部件库、中页面预览、右属性面板）；组件拖拽 + 属性面板模式经过充分验证。
  • 短板：面向表单字段而非文档版面；A4 分页 / 页眉页脚 / 章节流不是它们的模型。
来源：Everright-formEditor 介绍 · layui-form-design · vue 表单设计器思路

对照观察（不推荐引入）

Templatical / vue3-email-template-editor（MJML 邮件模板，面向 HTML 邮件非 docx）；pdf_kit_editor（Flutter 移动端）；shadcn Form Builder（React 生态开发向）。这些与「docx 原生保真 + 本地离线 + Python 栈」约束不匹配，仅作模式参考。

对比结论：没有现成方案同时满足「docx 原生保真 + 无 UI 全功能 + Python 栈 + 本地离线」。因此推荐组合式落地：取 C 的渲染底座（项目 tech-export 已是），取 D 的三栏交互范式用于预览原型，取 A/B 的「设计 JSON 为权威源 + 渲染引擎分离」作为架构骨架——四者的交集正是项目已有四件套的延伸。

推荐落地方案：模板描述 JSON + 渲染引擎 + 预览工作台

三层架构（示意）：数据源层为权威源；渲染引擎层完成校验 → 渲染 → 回读；UI 层只读视图，无 UI 时功能全走 CLI / Agent 对话。方向箭头表示数据流：模板描述 + 预设 + 部件 → 引擎；引擎状态 → UI 预览。

数据模型草案：template.json（v0.1 建议）

字段说明来源/规则
schema / version模板描述协议号与版本与 layout-presets.json 同构，统一由校验器约束
structure[]文档结构编排：部件序（cover/colophon/toc/body/section-closing），每部件可带 pageMode / 页眉页脚引用部件清单来自 parts/ 目录 + M2 台账；缺失校验报错
styleRef引用版面预设（preset/palette/font/headerFooter/微观六组）值域 = layout-presets.json 各组 id，缺省回默认组合
placeholders{}占位符绑定：企业名/项目名/章节流/图片位 → 部件内锚点与 M2 占位符台账对齐；渲染时从项目上下文回填
rules{}约束声明：暗标双态、图片缺失降级、表格超宽降级等复用 rules_base / rules_chapters 现有规则
provenance来源与历史（基于哪套模板、何时由谁设计）写日志，支持回溯

  • P0 数据模型与引擎

    template.json schema v0.1 + tpl_design.py（校验/存组合/暗标派生）+ export.py 模板驱动分支 + 单测 12 例。产出：《M6-模板设计-数据模型.md》。

    cli tpl-design 五子命令 + SKILL.md §7 工作流 + 样张直出回读断言（集成测试）+ 操作手册。此阶段无需 UI 即完整可用。

    /api/template/* 接口注册为平台工具（豆包已注册工具 / WorkBuddy 自定义技能），Agent 对话即设计器（对标《UI对接Agent平台方案报告》）。
