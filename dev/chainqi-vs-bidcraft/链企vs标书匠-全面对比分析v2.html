结论先行

三句话读懂这份报告

① 链企最强、最值得抄的不是某个功能，而是一整套「失败即报错」的工程纪律——它的 221 条爆雷几乎全部源于静默降级 （解析失败当空内容、截断不标记、写盘失败只 log、查不到当没有），而它被事故锤炼出来的正面做法 （写前快照、原子写+文件锁退避、统一错误码信封、检查契约结构化、引用回执、幂等对账）全部可无云端依赖地落进 bidcraft 的本地 CLI。

② bidcraft 的架构选择（本地单机 + CLI 单一事实源 + 人工确认闸门）恰好站在链企反面教材的对立面—— 链企的云脑中继、无人值守免确认、165 处 innerHTML、自动更新静默替换，在本项目里要么不存在、要么被白名单闸门结构性挡住； 需要抄的是它「写保护、状态机、结构化检查」这些与云端无关的部分。

01写前自动快照 + 回收站三段式重写安全网（章节历史版本控制）证据：B2 · H6 · I14-M5 · I22b · H1-P4
① 做法是什么
所有写章节/中间稿的路径挂前置钩子：写盘前先把旧内容快照到 .history/{章}/，同文去重 + 2 分钟同 reason 合并窗口 + 空文件不快照 + 每章上限 20 版；全文重写前先把旧正文整体搬入 .rewrite-trash/{runId}/（prepare 搬移记 manifest → commit 写新 → cleanup 清 trash，任一步失败按 manifest 逆序回滚）；撤销 = 读最新快照写回，撤销本身也进历史（双向可撤销）；纯运行态字段（status/字数/runId）写盘时 skipHistory，历史里只留内容版本。
② 原理
AI 生成是概率性操作，整批重写一旦中途失败不留旧稿就是净损失；「覆盖即备份」的事务化让磁盘上任何时刻要么有旧稿要么有新状态、不会两空。快照四道防抖（空/同文/时间窗/force 特例）把版本压缩到「真正有内容变化」的节点，避免 AI 流式分段写把历史刷爆。
③ 本项目收益
落到 m6_tech 的 tech-rewrite / tech-draft（cli.py:406、draft.py:675）：重写前先快照到 .history/、整批重写先搬 .rewrite-trash/，失败自动还原；m10_remedy 补救重检前留底；版本索引 JSON 与现有 m9 台账风格一致，直接替代当前「覆盖即丢失、错了找不回」的状态。
④ 大白话 + 示例
就像改标书前先把整个「正文」文件夹复制一份压箱底——万一新版写砸了，把箱子里的倒回来就行。
改造前：bidcraft tech-rewrite --all 跑到第 8 章模型超时，第 1~7 章已被覆盖成未验证的新版，旧稿全丢。
改造后：同命令先自动把旧正文搬进 .rewrite-trash/20261024-001/，任一章失败即按清单还原；用户说「退回上一版」= 读最新快照写回，这次退回本身也留底，能再退回来。

02原子写 + 文件锁五档退避 + 坏 JSON 不覆盖（写盘安全四件套）证据：B1 · B2 · D4 · D1 · H6 · I11 · I14 · I15 · I18 · I24 · I26 · I28 · I31
① 做法是什么
所有 JSON/台账落盘统一走：写临时文件 → fsync → rename 原子替换；写前把上一版存 .bak；遇 EPERM/EACCES/EBUSY 按 [20,40,80,160,320]ms 退避重试 5 次后抛 FILE_LOCKED；进程内 key 锁 + 跨进程 lockfile（PID+时间+心跳，stale 30s 可抢占）双保险；读取时先校验 schema 版本与形状，坏 JSON 抛 SIDECAR_CORRUPT、原文件不动、备份 .corrupt-{ts}，绝不拿空内容盖上去。
② 原理
直接写目标文件一旦中途断电/被杀就是半截 JSON，下次解析失败；tmp+rename 同目录原子替换，要么旧版要么新版没有中间态。Windows 本地现实：Word/杀软实时扫描会锁文件，立即重试必败，短退避后才放得过；双开两个进程写同一文件时纯内存锁挡不住，必须跨进程 lockfile。
③ 本项目收益
落到 m5_project 项目台账、m1_assets 入库 JSON、confirmLog、layout-presets.json / template.json（共享资源）、执行桥 write confirm 闸门后的落盘：全部收进一个 atomic_write_json() 工具函数；docx 中间稿写盘遇占用自动退避而非直接报错退出。
④ 大白话 + 示例
就像往标书袋里换材料——以前当着评委面把旧材料抽出来、新手还没塞进去，评委看到空袋；现在是先把新材料在旁边整理好（.tmp），整理完整后一秒换袋（rename），评委永远只看到「完整旧袋」或「完整新袋」。
改造前：json.dump(open('template.json','w')) 写到一半程序崩了，template.json 变半截，下次打不开。
改造后：先写 .tmp → 原文件改名 .bak → tmp rename 成正式文件；被占用时等 20ms 重试到 320ms（用户多半已保存关闭）；发现文件已坏则标 SIDECAR_CORRUPT 并从 .bak 恢复，绝不静默覆盖。
落点：m5_projectm1_assets共享资源 JSONdocx 中间稿
03统一错误信封 + 稳定错误码 + 禁止静默 catch（错误出口一统）证据：I9 · I23 · I19 · I14 · I12 · H1 · I5
① 做法是什么
所有跨边界调用统一返回 {ok:true,data} / {ok:false,error:{code,message,retryable,requestId}}；code 用稳定枚举（如 EXPORT_EMPTY_BODY），新增码先登记码表再使用；任何 catch 不得返回空对象/空数组继续执行；可降级的部件失败写 degraded[] 并进报告可见，必需部件缺失才硬阻断。
② 原理
链企的教训是三层错误壳（服务端五套 → 主进程 throw → IPC 序列化 → 渲染层正则剥前缀）每层都在丢字段，最终用户看到的文案与真实原因隔三道翻译；「机器可分流的 code」和「人可读的 message」从一开始分开编码，跨边界不解析就不丢字段。
③ 本项目收益
落到 scripts\bidcraft_server.py 的 POST /api/exec 返回体（现在是裸 stdout 文本，改造后前端能按 retryable 自动决策）；m7_check / m9_verify / m10_remedy 校验结果全部带稳定 code；与现有 write confirm 闸门配合，把「闸门拒绝/read 成功/write 待确认/高风险 deny」四种结局都变成可机读状态。
④ 大白话 + 示例
就像快递单号——出问题一扫就知道卡在哪个环节，而不是只看到一句「包裹找不到了」。
改造前：exec 返回一句「章节未进入编写流程，请重试」，前端只能原样显示，无法判断要不要自动重试。
改造后：返回 {ok:false,error:{code:"CHAPTER_NOT_STARTED",retryable:true}}，前端看到 retryable 就等 30 秒重试；所有 code 都能在 HTML 审查报告里定位到是哪个模块抛的。
落点：bidcraft_server.py /api/execm7/m9/m10 错误出口
04提示词四纪律 + {{待填}} 人工占位 + 解析失败语义显式证据：H1 · F1-P2 · D4 · I6 · I17
① 做法是什么
所有生成类提示词共用系统前缀四纪律：①只输出被要求的内容；②事实与推断分离，原文没写的一律不编造、缺失标「缺失」；③JSON 必须可机读直解不带代码围栏；④引用材料用【材料:名称】标记，禁虚构证书编号/金额/日期。材料没有的数据写 {{待填:说明}} 交人工补齐；解析失败显式输出 {"error":"内容不可解析"} 而非空内容。
② 原理
LLM 的失败模式有两种——真空和假空（解析失败被当成没内容）；不区分这两种，模型就会拿幻觉补全，这比报错危险得多。数据纪律把「缺」变成显式占位而不是编造，把人的补位从「全文找漏」压缩成「扫占位符」。
③ 本项目收益
落到 tech-draft / tech-rewrite 提示词模板（把现有「不得编造」升级为四纪律完整版）；m4_tender 解析返回 {text, truncated, totalChars, parseError}；M7 检查成稿前扫 {{待填 残留作为废标风险项。
④ 大白话 + 示例
就像资料员写标书，宁可在缺业绩的地方贴一张黄色便利贴「待补：近三年类似合同」，也不能瞎编一个——评委一查合同编号就废标。
改造前：提示词只写「不要编造」；模型读到一段解析乱码的招标文件，默认它就是没说，自行虚构「工期 540 日历天」；30 万字招标文件截断到 14 万，AI 以为读全，后半截评分点全漏。
改造后：解析层先返回 {error:"内容不可解析", truncated:true, totalChars:203000}，M7 直接红色告警「招标文件截断，缺失约 6 万字」；正文缺数据处留 {{待填:工期天数}}，检查报告列出 3 处待填交人工。
落点：m6_tech 提示词模板m4_tender 解析契约M7 待填扫描
05运行台账（run_settled 终态 + 慢调用阈值 + 结构化 JSONL）证据：I9 · I23 · I11 · I31 · E1 · D5
① 做法是什么
每次 run/命令执行终态写一条结构化台账记录 {ts, runId, kind, status, durationMs, projectId, bidId, chapterId, errorCode, requestId, retries, degraded[]}；执行桥对每次调用计时，超 3 秒记 slow 标记（slow_ipc 阈值）；日志统一 LogEntry schema（event 走枚举表禁自由文本），JSONL 落盘、7 天保留、5MB 轮转，丢弃/裁剪发 logs_dropped 计数不静默。
② 原理
技术标主链唯一稳定可用的细粒度观测就是 run 终态一行字——事后排障不用翻几千行日志；3 秒慢调用阈值把「卡死」从感觉变成可计数事件。本地单机没有云端也能享受：本地全量日志本来就是观测链第一段。

N1云端 Agent 中继（云脑 + 本地手，wss 远程下发工具执行）证据：D5 · F1 · H11
① 做法是什么
云端 WebSocket 网关按 token 认证，向客户端下发 tool.exec / shell.exec / file.read|write 等原始工具；主进程 10 个原始工具无沙箱、无确认、路径不收敛、子进程继承全量 env（含 token）；后链路 6 条 run 标 unattended:true 免用户确认直接执行——设计意图就是「远程终端」。
② 为什么不能实现
本地单机 Windows + 无云服务 + 无登录/计费：没有云端 Agent 可连，也没有 token 体系；且链企自己将其定性为「设计级 RCE」——网关一次越权或 token 泄露 = 全量客户端被控（D5 §1），这不是值得追的目标。
③ 替代方案
bidcraft 执行桥 v3.0（127.0.0.1 本地 HTTP 桥 + POST /api/exec 白名单 + confirm 闸门 + deny 表）就是等价且更优形态——动作发起方永远是本机用户点按钮，不存在「远端下发」这一层，token 外泄/网关失陷整类风险直接消失。
④ 大白话 + 示例
链企像「家里装了云端遥控器，云那边随时能指挥你电脑干活」；bidcraft 像「遥控器只在客厅茶几上，按下才动」。投标比方：链企模式 = 总部随时远程打开你的标书柜改文件；bidcraft = 柜子钥匙就在你自己手里，每开一格都要当面确认，总部连不上这台柜子。
N2SSE 流式三姿态续传（fresh / resume / cold-continue + 事件日志回放）证据：H7 · I15 · I19 · I12
① 做法是什么
长任务（批量写作）断网后不靠重跑，按 streamId + seq 游标从服务端事件日志回放续读（resume）；流的 owner 进程死了按 runId 认领新流接着跑（cold-continue）；配套 idle/hard 双闸看门狗（idle 每帧重置衡量「流还活着吗」、hard 从不重置衡量「任务还值得等吗」）、终态契约（没收到 done/error 即异常触发续传而非假装完成）。
② 为什么不能实现
无云服务端 + 无 Redis/事件日志：续传依赖服务端按 streamId 持久化事件并支持回放；bidcraft 的 LLM 调用是一次性 HTTP 请求而非长连接 SSE；执行桥是 127.0.0.1 本地短请求，不持有事件日志。
③ 替代方案
本地文件状态机 + generationRunId 归属戳实现断点续跑：中断后重跑命令，从 sidecar/状态文件读哪些章是 INIT/QUEUEING 继续、FINISH 跳过（对应引入项 5 的状态机化）；可借鉴纯客户端部分——双闸超时（idle/hard 区分）+ 分类退避重试 + abort reason 结构化，落到 m6_tech 的 LLM 调用。
④ 大白话 + 示例
链企像打电话——断了线，重拨后对方能接着刚才的话头说；bidcraft 像发微信——消息发出去就结束了，断了就是断了，但你可以看聊天记录（本地状态文件）知道哪些已读哪些没发，重发没发的。示例：tech-draft 跑到第 8 章崩了，重启后读 sidecar 发现 1~7 章 FINISH、第 8 章 INIT，从第 8 章继续——不需要服务端回放，因为每章结果已经落盘。
N3云端语义查重算法本体（tender_doc_sim 五步任务协议 + 双通道进度）证据：I4 · I26 · I14-M16 · E2
① 做法是什么
查重直连云端专属服务 tender_doc_sim：预检→创建任务落盘→上传→冻结计费→启动→WS 进度推送（+3s 轮询兜底）→报告；核心是语义级比对（embedding 向量）、图片感知哈希、RSID 提取，全部在服务端黑盒，客户端只做编排与报告归一。
② 为什么不能实现
无云查重服务 + 本地单机：语义级算法需要大模型推理服务或专用算法服务，本地无法等价提供；WS 实时进度通道对本地 CLI 也无意义（本地直接算）。上版候选⑨「本地查重」据此收窄：算法本体证伪，仅参数面/报告契约可复刻。
③ 替代方案
落引入项级：导入内容 hash 去重（fileId=sha256 前 12 位 + 「N 份重复已忽略」显式提示，I26）+ 本地字符级相似度（difflib / n-gram Jaccard，python 标准库起步），输出 pairwise 重复率矩阵 + 片段双栏对照 + 风险分档（>30% 高 / >10% 中，阈值进 rules.json），报告 HTML 化——并明示「本地字符级查重，非语义级」。
④ 大白话 + 示例
链企把稿子送到云端查重机房出报告；我们没有机房，能做的是拿尺子在家量两段文字重合了多少字——大段雷同、整句复制能量出来（已经够用），语义改写级的「换个说法但意思照抄」量不出，如实标注即可。示例：bidcraft check dedupe 输出「第三章↔第五章 重复率 35%（高风险），相似区间 1230-1450 vs 890-1100」，片段双栏高亮——像老师批作文查重系统，把哪两段哪几句标红摆出来，而不是只说「你抄袭了」。
N4服务端并发编排（15 路并发一键编写 + 双维并发桶 + 章节级取消）证据：A4 · I11 · I14 · A2
① 做法是什么
选一个项目数十到上百章，点一次按钮 15 路 worker 并发生成，按 {perProject, global} 双维桶限流，awaiting_question 不占桶、桶满 FIFO 排队；配套章节级取消（停一章其余照写）、互斥 claim（同章不重复跑）、AbortController 管理在飞流。
② 为什么不能实现
本地单机 CLI 串行流水线 + 无 Electron 渲染层/服务端调度器：并发批量写章需要 15 路 LLM 流并发管理、跨进程状态广播，这是 Electron 主进程+渲染层架构才有的东西；本地也无 LLM 配额池，15 路并发无意义且会把本机额度/磁盘打满。
③ 替代方案
保持 T11~T22 串行，但借鉴 A4 的「章节状态机落盘 sidecar」支持断点续跑——跑到哪章崩了，下次从最近未完成章继续（引入项 5）；需要异步时由执行桥 POST /api/exec 白名单 + confirm 闸门控制。
④ 大白话 + 示例
链企是「开 15 个工人同时写 15 章」，bidcraft 是「一个老师傅按顺序写 30 章」——一个人写手酸要吃饭，不能像 15 人那样并行；但可以借鉴「每章写完在墙上画个勾」（sidecar 状态落盘），吃饭回来接着画勾，不用从头重写。
N5专家团提示词服务端按团分发（客户端只传 ID、正文永不落地）证据：H2 · C5 · C3
① 做法是什么
专家团的章节提示词正文存服务端 contentPromptDataId，客户端每次写作只把 expertGroupId 上送，服务端按团解析拼装；更新提示词 = 服务端改一处全端生效；企业版可编辑自己团提示词并多版本发布/回滚。
② 为什么不能实现
CLI 单一事实源 + 无服务端：「客户端只传 ID、知识在云端」的前提是长期运行的服务端按 ID 解析；bidcraft 所有提示词必须本地可读、可 diff、可版本控制，否则违反「单一事实源」纪律；且链企自身反面（缺失时静默回落官方团 C5-2/H2-2）恰是 bidcraft「失败即报错」要避免的。
③ 替代方案
本地 taxonomy/styles.json + 提示词文件多版本：m6/prompts/施工组织设计/v3.md 为 current，tech-diff 直接 diff v2 vs v3，revert 把某版本软链为 current；「开发版即刻生效」等价为本地改完 prompt 文件立即对下一次 T12 生效，无需任何发布动作。
④ 大白话 + 示例
链企像连锁餐厅——菜单（提示词）总公司掌握，分店只传桌号 ID；bidcraft 是自家小馆，菜谱就贴在厨房墙上（本地文件），改菜谱直接改墙。示例：链企改「质量管理」章写作风格 = 服务端改一条记录；bidcraft = 改 prompts/tech-chapter-quality.md，改完跑全量回归 895 绿即生效。
N6云端商机检索 / 订阅推送（标讯库 + 定时任务主动推送）证据：C1 · C4 · C2
① 做法是什么
对接云端标讯库（招标公告/中标结果/采购意向等 11 类 tab）、企业画像/工商司法情报，订阅体系按「关键词+排除词+地区三级+金额区间+时间区间+行业+业主类型+匹配模式」过滤，定时任务按 cron 主动推送「上次推送后新增」的标讯。
② 为什么不能实现
无云服务、无外部数据源、无定时任务调度器：检索/订阅/推送全部依赖其 BFF + 标讯数据库，这是商业产品的基础设施层，不是本地 CLI 能补的。
③ 替代方案
把订阅方案字段结构抽成本地「商机登记台账」schema——用户手动粘贴标讯标题/链接/地区/金额后入库，m4_tender 按本地台账字段过滤高亮，不做主动发现；每次入库自动记 firstSeenAt，M9 报告列出「自上次 M5 归档后新增 N 条」。
④ 大白话 + 示例
链企像「订阅了 RSS 的新闻 App」自动给你推招标信息；bidcraft 像「自己做了个 Excel 台账」——你看到什么标讯手动记进去，但台账的列（关键词/排除词/地区/金额区间/时间窗）是照着链企那套设计的，以后想迁回任何系统都能用。示例：opps.jsonl 一行 = {keyword:"深基坑", exclude:"咨询", region:"马鞍山", amountMin:500w, firstSeenAt:"2026-10-24"}。
N7计费体系（积分冻结 → 实扣 → 冲正 + 402 资金闸）证据：I14 · I25~I28 · I29 · I12
① 做法是什么
发起 AI 请求前先按预估 token 冻结额度（billing.state: none|frozen|settled|refunded），执行成功实扣、失败/取消冲正；cycleId/idempotencyKey 防重复扣费；402 时撤在飞任务并冲正；价目表带版本随 run 快照。
② 为什么不能实现
无云服务、无登录、无计费、个人开发者本地工具：不存在「余额/积分账户」这个对象；CLI 命令不向用户收费，也没有可对账的账务系统。
③ 替代方案
「先确认后动作」哲学平移为已有的人工确认闸门（write confirm:true / 高风险 deny）；「冻结-回滚」纪律迁移到文件安全（引入项 2 的 .bak+rename、引入项 1 的 trash 三段式）；另做用量记账：run 台账记录每次调用 tokens.in/out 与成本估算，HTML 报告里记一笔「本章消耗 3200 token，约 0.4 元」。
④ 大白话 + 示例
链企像打出租车先扫码预付费再走、退菜退定金；我们是私家车不涉及车费，但「跑一趟 2 小时的长途要不要现在出发」这个确认动作保留——不扣钱，但出发前问一句，防止误操作跑飞；每次跑完记一笔花了多少油钱（token 用量），月底自己能对账。
N8自动更新双引擎（OSS 拉包 + sidecar/schtasks 脱离父进程 + 版本对账）证据：D1 · F1-§12.3 · V-§6 · E1
① 做法是什么
Electron 应用后台轮询探版本（15s 首检/5min 间隔），OSS 直下 zip + sha512 校验 + .part→rename 原子落盘，sidecar/schtasks 三级拉起脱离父进程、目录整体 rename 交换安装，装后对账版本号并把坏版本拉黑。
② 为什么不能实现
非 Electron 应用 + 无安装形态/OSS/分发体系：bidcraft 是本地 Skill 项目，分发靠本地等效同步（E:\标书匠生产 独立 git sparse-checkout），没有「更新一个正在运行的程序」的需求；且链企自身事故史证明这是纯风险面——隔离副本被官方升级器静默替换（F1 §12.3）、实机验证触发自动升级替换生产安装（V §6）。
③ 替代方案
git pull / 本地目录同步即「更新」（生产 = GitHub main → deploy runner + 6h 计划任务兜底，bidcraft-facts §5）；借鉴两条局部手法：写文件 .tmp→rename（引入项 2）、启动时 M9 体检核对 layout-presets.json/template.json 版本一致性，对不上显式打印告警而非静默继续。
④ 大白话 + 示例
链企像「写字楼里的公司，每天凌晨自动派人把整层办公室的家具换新，换新失败就把这批家具拉黑」；bidcraft 是「自己书房，要换家具自己去搬」——上版结论「自动更新不做」在本轮获得最强佐证：它在链企文档里是事故源而非能力。
N9AI 生图/配图体系（章节配图 + 封面 AI 出图 + 工程附图生成）证据：H5 · I27 · I28 · I24 · I21
① 做法是什么
正文写完后对某章点「配图」，读正文→加载画风技能→逐张调图片生成 API（GPT_IMAGE_2）出图→文件名即图注→先落候选区、用户挑中才进正文；封面/页眉页脚由服务端 AI 生图黑盒产出（workflow.dag model 节点）；横道图/平面图由服务端黑盒生成。
② 为什么不能实现
无图片生成 API 集成 + 无画风技能注册体系 + 无云端 AI 出图服务：技术标以文字+表格+流程图为主，配图通常由 CAD 导出或素材库提供而非 AI 生成；个人开发者无图片生成 API 预算；平台无关打包也不允许依赖远端黑盒。
③ 替代方案
layout-presets.json 的 15 组×10 套版面预设中图片位置留占位符（如 [FIGURE: 图3-1 施工平面布置图]），用户手工插入 CAD 截图/素材图，tech-export 渲染时占位符替换为真实图片位置；「候选区隔离、批次可回溯」思路保留给未来接入本地/开源生图能力时参考。
④ 大白话 + 示例
链企像请插画师——文章写完自动配插图；bidcraft 像写公文——图是自己从 CAD 截图贴进去的，不是 AI 画的。示例：第 3 章写完链企自动出 5 张施工平面图；bidcraft 是版式里留好图位，你在 Word 里插 CAD 截图，导出时版式稳定可复现——不追求「每张封面独一无二」，追求「每次导出版式一致」。
N10云端知识库同步 + 跨端乐观锁 409 冲突解决证据：I29 · I32 · I14-M19
① 做法是什么
云为唯一真相源、本地只读镜像（24h TTL）+ 待办队列 + 写穿纪律（云端 2xx 后才更新镜像）；文件带 version 乐观锁，写操作回传读到的 version，409 冲突时给「刷新查看 / 强制覆盖（二次确认）」两动作，默认不覆盖；跨端实时推送。
② 为什么不能实现
本地单机 Windows、无云服务：没有第二端就没有跨端冲突，BFF 真相源不存在；上版「云端同步不做」结论经 I29 全篇核对确认不翻案。
③ 替代方案
本地 project.json / sidecar 即唯一真相源；version 思想降级为 sidecar 单调修订号，防「本仓 + 手工改文件」的双写漂移；剥离云端后待办队列+幂等键+退避重放（[1m,5m,30m,2h,12h] 耗尽转人工）与引用对账四态（selected/ok/miss/failed 分开统计、删除素材前扫引用二次确认）可纯本地化移植——详见引入项 10 及下方速览表。
④ 大白话 + 示例
云方案像两本同时在两个办公室修改的标书合同——版本号对不上就弹「谁覆盖谁」；本项目只有一台电脑一份文件，这道弹窗永远不会出现，只需要记住「我这份就是最新版」。但链企同步设计里「打印机卡纸记在待补打清单、1 分钟后自动重试、凭幂等键不重复打已打好的页」这套本地化机制照样能搬。
