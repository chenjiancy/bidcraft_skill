三、值得引入的做法（原理 + 本项目收益）

以下 10 项按「工程价值 / 落地成本」排序，全部有链企源码锚点或详细设计文档支撑，均为 bidcraft 可以吸收为 skill/文档/代码三层能力、不依赖 UI 的做法。

1. 写路径统一闸口的章节历史快照P0

依据：B2（章节历史快照）

链企的做法

所有写盘统一走一个入口（writeFileOnDisk），写前自动快照旧内容：上限 20 版/章、同文去重、同因 2 分钟合并窗口防 AI 流式刷屏；图片按 sha256 内容寻址归档进版本、50MB/章预算从最老版本降级、GC 只删孤儿；回滚 = 读旧版 + 以 restore 原因写回，天然双向可撤销。

原理

「写前先留底」挂在唯一落盘闸上，任何 AI/人工写入都无法绕过历史；防抖与去重让高频写入不刷爆版本列表；内容寻址让图片不重复占盘。

本项目收益

  • 现在 tech-rewrite 只有 .rewrite-trash 单份备份——升级为 20 版快照后，任何一次精修/导出覆盖都可回滚，投标前改错了能找回三天前的版本；
  • 版本索引 json 可并入 m9-evidence 留痕包，评标质疑时拿出「哪一版是谁改的、为什么」完整证据链；
  • 纯 Python + 文件系统实现，无 UI 依赖，直接落地为 CLI（如 hist-snapshot / hist-list / hist-restore）。

2. 校验结果落地 + 显式状态机（RULE_CHECKING/AI_CHECKING）P0

依据：H13 §5-6、I16（质量闸设计）

链企的做法（反面起点）

链企质量校验在服务端黑盒：只有「质量校验未通过，正在修正…」的 UI 标记，规则不可见、无校验报告产物、失败处理不透明（H13-2/3/4/6 四条爆雷）。复刻设计 I16 把它显式化为：规则引擎 25 条 + GB8 条 + AI 语义四维双通道，校验不通过不得进入下一环节，结果落地 *.check.json，失败自动重写 ≤N 次再交人工。

原理

确定性规则毫秒级快速失败，AI 语义兜底"内容是否真贴合评分点"；状态机显式扩展（INIT→…→RULE_CHECKING→AI_CHECKING→FINISH/REWRITE/ERROR），门禁保证坏章节进不了下一环节；报告落盘让校验可审计。

本项目收益

  • 我们的 M7 已是最强项（双通道 + 技术标 13 项），缺口是「校验结果状态机化」：现在 check 是静态报告，引入 RULE/AI 两态与自动重写计数后，tech-rewrite 精修回路可直接消费"哪条规则没过、自动修了几次、还差什么"；
  • check.json 结构化后，M10 remedy-gen 的任务单生成可更精确（现在靠人读报告）。

3. 提示词工程纪律：事实/推断分离 + 材料标注 + 温度分档P0

依据：H1（提示词体系 P0~P6）

链企的做法

共用系统前缀强制：只输出要求内容、事实与推断分离、JSON 必须可 parse、引用材料用【材料:名称】标记、禁止虚构证书编号/金额/日期；抽取类提示词（解读/分类/缺口检测）温度 0~0.2 强制 JSON，生成类 0.5~0.7 输出 Markdown；上下文预算截断 14 万字符；缺失信息输出 {{待填:说明}} 交人工，禁止编造（对应 D4 幻觉补全爆雷的教训）。

原理

LLM 幻觉主要来自"没写的当成有"；把"材料里没有"显式建模成一种合法输出值，AI 宁可交付"待补"也不编数据——这是标书这种零容错文书的底线纪律。

本项目收益

  • M4/M6/M7/M8 提示词已有版本化与固化，直接吸收四条硬纪律（JSON 围栏禁令、【材料:名称】标记、{{待填}} 占位、温度分档表）到 v1.1 各提示词文件，一行都不改架构，纯文案强化；
  • 和商务标「确定性原则」（用户最高优先级）完全同向。

4. 知识库消费链：章级引用指针 + 写作时回源 + 三级回落 + 引用回执P1

依据：I10（知识库消费链）

链企的做法

技术标「以标写标」：目录 sidecar 只存引用指针（fileId，content 恒空瘦身）→ 写作时 4 并发回源拉取、1 万字截断 → 三级回落（章级 referenceLevel ?? 章 feature ?? sidecar 存档）→ 服务端回执写 正文/.meta/{章}.reference.json 记录每章实际引用；low 档不上行省 token；上溯继承（父章配参考子章自动继承）。

原理

指针存储 + 回源 = sidecar 不膨胀、正文不落版权内容；回执 sidecar = 每次写作实际用了哪些资料可审计；三级回落 = 缺一级不崩。I10 同时给出必反做：拉取失败/截断必须冒泡提示，不能静默（链企静默家族五条爆雷）。

本项目收益

  • M3 知识库（共享级）正是剩余清单第 1 项——这份文档就是 M3 消费侧的完整施工图：引用配置→回源→回落→回执→对账，可直接写成 references/M3-知识库-消费侧设计.md；
  • 结合现有 M4 素材清单驱动与 M10 入库沉淀，形成「素材→引用→回执→入库」闭环。

5. SSE 双闸 + keepalive + 终态契约（长任务不误判）P1

依据：H7（SSE 流式协议）

链企的做法

idle 闸（任何字节到达即重置，含 keepalive 注释帧）与 hard 闸（创建起倒计时不重置）分离；服务端 15s 一帧 keepalive，模型长思考不误判；终态是契约——流结束但没收到 done/error 就算异常，触发续传而非假装完成。

原理

「连接死了」和「任务太慢」是两种故障，一个闸说不清；keepalive 让 idle 可以安心设短，终态契约让静默失败变成显式异常。

本项目收益

  • 现在 tech-draft/tech-rewrite 是 CLI 一次性调用 agent 平台，长时间任务无进度心跳——把「双闸 + 心跳 + 终态校验」下沉为通用调用封装（如 agent_call.py 统一超时/重试/终态判定），所有模块复用；
  • 未来接入流式输出时（server 桥扩展）协议层直接对齐，不重写。

6. 统一错误码表 + 错误帧单入口归一P1

依据：I14/I31（150 个唯一错误码）、H7 §5（错误归一化）

链企的做法

全系统 150 个唯一错误码，新增必须先登记再使用；所有流式错误帧剥掉内部字段后经唯一入口解释下发给 UI，客户端各消费方不各自为战。

原理

错误格式只有一个解释点，排障信息可索引、可统计（哪个码高频出现就是哪个模块要修）；错误码表本身是跨模块契约。

本项目收益

  • 现在各 CLI 报错风格不一（有的裸 traceback、有的中文一句），统一为 错误码表.md + 每个命令 fail fast 带码输出（如 OUTLINE_EMPTY），m9-evidence 留痕包自动汇总本单出现过的高频错误码；
  • 成本低、见效快，是纯文档+收尾工程。

7. 原子写 + 退避重试 + 跨进程锁（M9 持久化纪律）P1

依据：I31 §5（原子写）、H1 P4（20/40/80/160/320ms 退避）

链企的做法

写盘统一 tmp+rename 原子替换；EPERM/EACCES/EBUSY 按指数退避重试 5 次；跨进程 lockfile 防双开；坏 sidecar 可修复。

原理

半截写入 = 下一次读取的静默坏数据；退避重试把 Windows 上常见的文件占用（Word/杀软）变成自愈而不是报错。

本项目收益

  • Windows 真实环境（Word COM 常驻、杀软扫描）正是这类问题的重灾区——抽一个 atomic_write() 工具函数 + with_file_lock()，替换各命令裸 open() 写盘，写后回读本来就已做，叠加原子写后彻底消除半截文件；
  • 生产目录 E:\标书匠生产 与项目双开协作时，锁防止两份同时写同一项目。

8. 商务标「本地快照即真相」写作期不拉远端P1

依据：I10 §3（reference-bids.json 本地快照）

链企的做法

商务标历史参考写成 正文/.biz-doc/context/reference-bids.json 本地快照，写作时直接读快照注入上下文，云端增删不影响进行中的写作（I10 同时点名：快照解析失败必须显式报错，不能静默退化为空数组）。

原理

「写作期不拉远端」把外部依赖从热路径上移除——快照即真相，断网也能继续写；这是把不确定的外部系统隔离在开始之前。

本项目收益

  • 等价理念已是我们的设计基线（素材清单驱动 fill-tpl、冻结项目模板），但可以补一个显式动作：生成商务标前把 M1 素材台账命中项快照为项目级 素材快照.json（含版本时间戳），后续任何检查/补救都以快照为准，避免"写一半素材库变了"；
  • 快照文件并入 m9-evidence 留痕包。

9. 模板/素材入库的幻觉防线与幂等标记P2

依据：I10 §4（模板入库）、I31 §5（幂等）

链企的做法

failed/error 状态的产物禁止保存入库；保存动作以服务端返回的 id 为准才标记成功；每类任务一个幂等键公式，终态置空防重复扣费/重复入库。反例是链企自己把「已保存」标记放 localStorage（换机即丢，I10-7 爆雷）。

原理

入库动作必须有服务端/权威侧确认，本地乐观标记不可信；幂等键保证同一产物重复操作只有一次生效。

本项目收益

  • M1 apply --proposal / M2 模板登记 / M10 assets-archive 已有确认闸门，补充两条硬规则：入库申请单条目在应用前必须复核产物状态（如 docx 可打开、图片非空），入库后写幂等标记到台账（防同素材二次入库）；
  • 把「已入库」状态从产物名/目录推断改为台账字段权威。

10. 观测里程碑：每个 run 8 条里程碑 + 终态必达P2

依据：I31 §5、I23（观测设计）、H13 §4.4

链企的做法

每次 run 必留 8 条里程碑事件，终态必发 run_settled；章节状态机严格流转（INIT→QUEUEING→GENERATING→FINISH/TIME_OUT/ERROR/CONTENT_EMPTY），非法流转被拦截。

原理

「没到终态」本身就是故障信号；里程碑让一次 run 的每一步可回放，排障不需要人肉回忆。

本项目收益

  • m9-evidence 已做产物索引（静态），升级为「运行台账」：tech-draft/rewrite/check 每次执行追加一条 run.ndjson（起止/状态/耗时/产物 hash），投标留痕包直接读它渲染时间线；
  • 终态契约保证每个命令要么成功要么带码失败，不存在"不知道有没有跑完"。

四、链企好但本项目无法实现的做法（原因 + 替代方案）

以下 6 项是链企确实做得不错、但受限于 bidcraft「skill+agent 平台、CLI 为主、无服务端、个人自用」的形态而无法照搬；每项给出原因和可行替代。第 7 小节列出链企「好在哪里但绝不能引入」的反面教材（安全爆雷与计费时序）。

1. Electron 桌面端原生 UI（所见即所得编辑器、流式打字机、瀑布流图库）

依据：C4（图库/知识库 UI）、A4（批量写作 UX）

为什么不能

前端 UI 已确认不对接 agent 平台、仅作演示原型；agent 平台（豆包/WorkBuddy）不提供可挂载的 GUI 沙箱，桌面安装包超出 skill 分发形态；流式打字机需要 SSE + 常驻渲染进程。

替代方案

  • HTML 报告/设计器原型已验证可行（版面设计器工作台、检查报告、模拟评标报告），把"可视化"落在产物层而非交互层；
  • shot.py 渲染截图 + artifact-preview 让 agent 和用户都能"看到"结果；
  • 未来若需要真 UI，再独立建 Web 前端消费 server 桥，与 skill 本体解耦。

2. 服务端 15 路并发写作 + SSE 断线续传 + 云 BFF 编排

依据：A4、H7、I31（M8 地基）

为什么不能

并发与续传依赖服务端事件日志回放（Redis 游标）与云端 agent 常驻；我们没有服务端、没有账号体系、无部署目标；agent 平台按对话调用，无 runId/streamId 语义。

替代方案

  • 保留确定性流水线：tech-draft 规则拼装 + 人工/agent 精修 + 闸门，串行但不丢；
  • 吸收 H7 的「双闸/终态契约/错误归一」到本地 agent_call 封装（见三-5），把断线语义本地化：单次调用设 idle/hard 双超时、异常必须带终态；
  • 「并发桶」理念降级为脚本内受控并行（如批量渲染部件用 ThreadPool 3~4），不引入状态机复杂度。

3. 云端知识库/图库/模板库 + 跨端云同步 + 引用对账

依据：C4、I29（知识库云同步设计）、I10

为什么不能

云同步需要账号体系、OSS、解析服务与 BFF；本地 skill 无云端身份，也不可能让用户的标书资产（涉密）上云（链企自己的 C4-1 爆雷就是"说本机存、实为云端"的合规争议——我们反而避开了这个雷）。

替代方案

  • M1 素材库 / M2 模板库 / M3 知识库本就是本地三层目录，M19 的「引用对账 selected/ok/miss/failed」可在本地实现（引用配置 vs 实际命中清单的差集明示）；
  • 「云」用「目录 + 命名 + 版本记录」模拟：素材库台账 + 校验和 + 生产同步 commit，跨机靠网盘/天翼同步盘（用户已有）；
  • 投标敏感信息留本地是架构优点而非缺陷，报告里明示。

4. 标书内容查重（tender_doc_sim 服务端相似度引擎）

依据：I4/I26（查重链路）

为什么不能

查重需要全文索引库 + 向量/规则引擎 + 原文跳转报告，链企实现是服务端 8+1 端点 + 写穿缓存三 sidecar；本地全量库会随标书增长失控，且无"全网历史标书"数据源。

替代方案

  • 本地范围查重可做但降级：企业级素材库 + 本企业历史标书 + 当前项目章节间的相似片段检测（如 python-difflib/余弦，章节 vs 素材命中度），产物并入 M7 检查（新增 tech_duplicate 检查项）；
  • 对外查重需求交给人工（专业查重平台），skill 提供"待查清单"导出。

5. 招标发现/商机订阅/定时推送（任务助手四助手）

依据：C4 §4（TaskAssistantPage）

为什么不能

需要外部标讯数据源 API、订阅配额、定时服务与邮件推送通道；个人无标讯账号与常驻定时器（cron 定时工具只做提醒，不做数据抓取）。

替代方案

  • 人工搜标 → tender-init 建项目 → tender-annex 归档补遗/澄清，把"发现"留给用户、把"归档解析"自动化（已实现）；
  • 可加一个「商机登记表」轻量台账（投标日历 + 截止时间提醒，用定时任务提醒），不做自动抓取。

6. 积分计费/先冻结后发起/超额扣费（商业模式层）

依据：I12、I25 §4.7、C4 §4.7（导出扣费）

为什么不能

个人自用无计费对象；但链企的「先冻结后发起、失败必冲正、价目随 run 快照」是优质工程实践，其反面（C4-13 先扣后知、I4/I5 扣费时序爆雷）正是它踩的坑。

替代方案

  • 用「人工确认闸门 + 版本记录 + 幂等键」替代计费闸：每个不可逆动作（应用归档/入库/导出覆盖）必须 --confirm，写后回读；
  • 运行台账（三-10）记录每次动作，充当"账单"。

7. 反面教材：链企做得好但不能引入（甚至要警惕）

链企做法为什么是好/坏两面的bidcraft 立场
服务端黑盒 prompt 与黑盒质量校验提示词全在服务端 scenes.ts、质量规则不可见——可快速迭代但对用户零透明（H13-2/3）提示词版本化 + Golden 样例 + 检查规则全部落盘可审，这是链企的教训而非优点，保持现状
49 条安全爆雷的代价221 条爆雷（13 P0）来自其 Electron+云端+IPC 的复杂面（E3 审计、D6 读侧无白名单）无 IPC/无云端/无账号，攻击面收敛——这是形态优势，不引入复杂面
先扣费后发起、导出先扣后知时序缺陷导致用户被静默扣费（C4-13、I4/I5）人工确认 + 零计费，无此问题；运行台账做等效账单
静默失败家族回源失败返 null、截断不提示、快照退化空数组（I10-1/2/3/5）我们的写后回读 + fail fast + 缺料披露正是链企缺失的，继续坚守"宁可打断不可无声"
localStorage 乐观标记「已保存」标记存本地，换机即丢、可重复入库（I10-7）台账字段为权威、幂等键去重（M1/M10 已有），补强即可

五、结论与建议路线

一句话结论：链企 Buddy 是一套工程完整但安全与透明欠账的商业产品；bidcraft_skill 形态不同但主链功能覆盖率已达 14/22 项（含全部核心做标环节），且在做标最关键的两点——确定性与可审计性——上反超链企（人工闸门 + 三层测试 + 留痕包 vs 黑盒 + 静默失败）。值得抄的不是它的功能壳，而是它被真实事故锤炼出的 4 类工程纪律：写前留底（历史快照）、终态契约（错误/流式/状态机）、指针+回执（知识库引用）、幂等与权威侧确认（入库）。

  • P0（两周内）：① 章节历史快照（hist 三命令 + 20 版上限 + 内容寻址图片）；② 提示词四纪律回灌 M4/M6/M7/M8 提示词；③ 校验状态机扩展（check.json 加 RULE/AI 态 + 自动重写计数）。
  • P1（一个月）：④ M3 知识库按 I10 消费侧蓝图落地（引用配置→回源→三级回落→回执 sidecar→对账，本地版）；⑤ 统一错误码表 + agent_call 双闸封装；⑥ 原子写 + 文件锁工具化。
  • P2（按需）：⑦ 运行台账 run.ndjson 并入 m9-evidence；⑧ 素材快照化（写前冻结）；⑨ 本地范围查重检查项 tech_duplicate；⑩ 商机登记表 + 截止提醒。
  • 明确不做：UI 编辑器、服务端并发/续传、云端同步、计费、自动更新、微前端——形态不允许，替代方案已在第四节给出。
